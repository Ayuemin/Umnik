## 0. Решение о переиспользовании Umnik и границах изменений

**Согласовано владельцем:** только один пользователь, обратная совместимость данных и старого UI не является обязательной, заявка F-Droid отозвана; размер APK не ограничивает функциональность. Это разрешает **архитектурную перестройку**, но не является согласием на потерю файлов без резервирования, небезопасные операции или публикацию.

**Состав сохраняемого ядра:**

| Подсистема | Стратегия | Текущий статус/условие |
| --- | --- | --- |
| Чат, история, вложения, Markdown/streaming | Перенести и упростить | Рабочие компоненты Umnik, проверить на Android |
| Русская офлайн-диктовка, TTS, темы, шрифты, звук | Перенести | Работающий прототип диктовки и интерфейс; проверить автономно |
| Keystore/секреты, безопасные файлы, фоновые запросы | Перенести и выделить контракты | Не давать tool прямой доступ ко всему хранилищу |
| OpenRouter, кеш и usage | Переработать в provider adapters и общий ledger | OpenRouter уже есть; универсальные API ещё предстоит подключить |
| `AgentToolHub`, `ToolRegistry`, `TaskGrant` | Развить существующие компоненты | Реальное выполнение покрыто частично, не выдавать за готовую шину |
| GitHub/Actions | Переработать в автономный adapter | Тест калькулятора не завершился APK; E2E ещё нужен |
| Local Browser | Технический аудит и выбор лучшего runtime | Частичный рабочий компонент; нужен security/Android E2E |
| Local Shell, Files | Перенести через общую шину и `ArtifactStore` | Проверить sandbox и обмен артефактами |
| Проекты/команды, расширенный RAG, Batch, видео, экспериментальное UI | Изолировать, затем решить судьбу | Не тащить автоматически в первую версию, не удалять без карты зависимостей |
| SSH/MCP и другие будущие инструменты | Добавлять новыми адаптерами | Не объявлять реализованными |

**Запреты:** ни полной переписи Umnik вслепую, ни массового удаления по названиям классов, ни новой конкурирующей шины, ни отклонения от принятого дерева без ADR. Сначала перенос функций и контрольный APK, затем чистка.

## 1. Суть продукта

**Следующая архитектурная версия Umnik** — Android-приложение с универсальным агентным чатом. Пользователь общается с моделью, выбранной у любого подключённого API-провайдера; модель самостоятельно задействует доступные инструменты для выполнения поручения. Инструменты — независимые блоки, зарегистрированные через единую внутреннюю шину. Один инструмент можно использовать отдельно, несколько — вместе, последовательно или параллельно. Инструменты не обязаны знать ни друг о друге, ни о реализации чата.

Пример: пользователь просит «Найди библиотеку на GitHub, создай из неё тестовый Android-проект, собери APK и приложи результат». Чат передаёт поручение агентному ядру. Координатор назначает действия Browser/GitHub/Shell/файлы, проверяет разрешения, сохраняет шаги и контекст, показывает реальный прогресс и возвращает конечный файл. Если сборка не прошла, агент исследует ошибку и продолжает, а не объявляет промежуточный результат завершением.

### 1.1. Главные свойства

- **Модульность:** одна ответственность — один компактный класс/функциональный блок; жёсткие границы Gradle-модулей, архитектурные тесты, запрет классов-«комбайнов».
- **Чат — база:** минимально необходимый UI, история и управление вводом; никаких ручных интеграций Browser/GitHub прямо в Compose.
- **Любые API-поставщики:** общие интерфейсы + самостоятельные адаптеры, а не привязка к одному агрегатору.
- **Автономность:** модель использует каталог разрешённых инструментов и сама выбирает порядок, параллельность и время обращения.
- **Практическая экономичность:** штатное prompt caching, сокращение повторов и объёма передаваемых данных, достоверная статистика токенов и расходов.
- **Прозрачность:** действия инструмента и статус появляются в процессе работы, а не только после финального ответа.
- **Расширение без деградации:** очередной инструмент подключается модулем/адаптером; ядро и чат не переписываются.
- **Android-first:** локальный координатор, хранение и разрешения; приложение не зависит от собственного постоянно работающего сервера. Сторонние LLM, удалённые API, MCP и пользовательские серверы возможны как подключения.
- **Функциональность важнее размера:** не устанавливать искусственный потолок APK; контролировать производительность, обновления и потребление памяти.

### 1.2. Не следует делать в первой версии

- Не переносить все функции старого Umnik в новый интерфейс одновременно; ценные существующие компоненты использовать как проверенные доноры.
- Не создавать конструктор с тысячами страниц настроек.
- Не делать самопереписывание/самоустановку произвольного кода через плагины.
- Не добавлять собственный обязательный облачный бэкенд.
- Не вводить обязательную вторую ИИ-модель для проверки каждого шага: основная модель может сама планировать и проверять; отдельные специализированные модели — необязательная оптимизация.
- Не объявлять готовность браузера или GitHub только потому, что существует работающий интерфейс.

## 2. Архитектура: дерево прежде кода

**Обязательный файл: `PROJECT_TREE.md`.** Он содержит целевое дерево Gradle-модулей, примеры небольших классов, зависимости, список запретных импортов, порядок выделения модулей и правила добавления tools.

### 2.1. Логическая схема

```text
Пользователь
   ↓
Чат / UI / ввод и вывод (без бизнес-логики инструментов)
   ↓ события / команды
Агентное ядро: якорь поручения + план + контекст + проверка результата
   ↓
Координатор задач: последовательность / параллельность / восстановление
   ↓
ToolBus: каталог → выбор tool → проверка прав → исполнение → события
   ├─ Browser adapter ─ Android WebView / наблюдения / действия
   ├─ GitHub adapter  ─ REST API / Actions / артефакты
   ├─ Shell adapter   ─ локальная ограниченная среда
   ├─ Files adapter   ─ SAF / локальные файлы
   ├─ SSH adapter     ─ удалённые сессии
   └─ MCP/other       ─ новые подключения
   ↕
ArtifactStore, SecretVault, TaskStore, UsageLedger, EventLog
   ↕
ProviderRegistry → OpenAI-compatible / OpenRouter / Anthropic / Gemini / future
```

**Направление зависимостей:** `app` собирает реализации; `features:chat` → API ядра; `core:agent` → интерфейсы провайдеров и tools; `tools:browser`/`tools:github` не имеют зависимостей друг от друга и от `features:chat`. На старте старый `:app` остаётся точкой сборки Umnik; реальные Gradle-модули выделяются небольшими шагами, с временными адаптерами к legacy-коду и последующим их удалением.

### 2.2. Политика размера кода

- Обычный класс/файл: примерно 80–300 строк. При 400 строках проверить необходимость разделения. Более 600 строк — отдельное обоснование в ADR и CI-исключение; запрещено обходить правило генераторами или разбиением на бессмысленные файлы.
- Один бизнес-сценарий может содержать несколько небольших классов: интерфейс, политика, реализация, parser, mapper, tests.
- Не требуется буквально «класс на каждую функцию»; простые чистые функции можно держать рядом с тесно связанным типом.
- Каждый публичный контракт документирует входы, выходы, ошибки, таймауты, отмену и ресурсы.
- Один реестр ошибок, одна система логирования, одно хранилище артефактов; не плодить пять параллельных способов одной функции.
- Запрещены скрытые циклы между модулями и вызовы через глобальный синглтон с любыми правами.
- Обязательны строгая типизация, инъекция зависимостей, KDoc для публичных контрактов, unit tests.

## 3. Функциональность основного чата

### 3.1. Главный экран

Интерфейс спокойный и компактный. Центр приложения — переписка. Вверху: название диалога, компактное меню, доступ к истории/настройкам. Внизу: поле ввода, вложения, отправка, офлайн-микрофон. Вспомогательные настройки инструментов открываются отдельно, не занимают основную область.

Обязательно:

1. Диалоги с локальным сохранением, понятные названия, создание, переименование, поиск, удаление с подтверждением.
2. Ответы со streaming-текстом; корректное отображение Markdown, кода и ссылок.
3. Отправка текстовых сообщений; общий контракт для вложений/файлов. Список фактически поддерживаемых вложений зависит от provider capabilities, UI не обещает отсутствующие функции.
4. Операция остановки ответа; если выполняется агентная цепочка — отмена дочерних операций и сохранение результата/состояния без ложного статуса «успех».
5. События состояния `queued`, `running`, `waiting_for_model`, `tool_running`, `waiting_user`, `recovering`, `failed`, `completed`, `cancelled`.
6. История может возобновлять незавершённую задачу без повторного расходования денег на уже успешно выполненные шаги.
7. Выбор провайдера/модели (глобально и при необходимости для чата), поддержка моделей с tools и без них. Если tools недоступны, сообщать о несовместимости, а не имитировать вызовы.

### 3.2. Панель под каждым ответом

**Постоянно, компактно:**

- `Копировать` — копирует весь содержательный ответ, с сохранением кода/форматирования в текстовом представлении; при наличии нескольких файлов — не подменяет копирование их содержимого.
- `Озвучить` — воспроизвести текст ответа; повторное нажатие/кнопка остановки прекращает воспроизведение. Допускается Android TTS без платного API; любые платные голоса — лишь по выбору.
- `⋮` / «Ещё» — дополнительные действия. Включить: поделиться, сохранить текст в файл, повторить/перегенерировать, цитировать в новом сообщении, открыть «Об ответе», посмотреть прогресс и артефакты, выбрать текст. В будущем инструменты могут предложить контекстное действие «Обработать этим инструментом» только через утверждённую шину.

Без громоздкой панели из десяти кнопок. Меню расширяется без изменения MessageCard: через `AnswerActionRegistry` (без выдачи разрешений на исполнение).

### 3.3. Оформление и звуки

- Светлая/тёмная/системная темы, минимум несколько цветовых схем; без разрозненных цветов по файлам.
- Пользовательское изменение размера текста чата и выбора доступного шрифта, масштабирование с Accessibility/Android font scale.
- Звук готового ответа: включение/отключение, независимость от звука ожидания действий пользователя, корректная работа с режимом «Без звука», focus и notification permissions.
- Для фоновой готовности — уведомление, если это разрешено Android и пользователем.
- Нормальный показ клавиатуры, курсора, длинных сообщений, вложений и панели прогресса на небольших экранах.

## 4. Офлайн-диктовка пользовательского запроса

Обязательная локальная модель распознавания русской речи. Предпочтение — проверенной мобильной технологии (`Vosk`, `sherpa-onnx` или иной движок после сравнительных тестов по CPU, памяти, скорости и качеству на пользовательских устройствах). Это **распознавание речи в текст**, а не локальная LLM.

- Никакой передачи записанной речи в сеть во время распознавания. Модель может поставляться в APK или устанавливаться отдельным, явно подтверждённым пакетом с проверкой хеша; вариант выбрать по надёжности и удобству, не по экономии APK.
- Начало записи только после разрешения `RECORD_AUDIO` и прямого нажатия. Показывать активный микрофон.
- Частичные распознавания допускаются, но итоговый текст **сначала попадает в поле ввода**. Автоматически не отправлять его в LLM.
- Можно редактировать распознанный текст и комбинировать его с клавиатурным вводом.
- Работа без интернета, отмена записи, восстановление после поворота экрана/паузы, отказ от записи при утрате разрешения.
- Проверки на реальном Android: шум, длинная фраза, повтор записи, потеря audio focus, исходящий звонок.

## 5. Любые API-провайдеры через единый контракт

### 5.1. Концепция

Предусмотреть `LlmProvider`, `ProviderRegistry`, `ProviderConfig` и `ProviderCapabilities`. Новый поставщик — адаптер `providers/<name>`, не изменение реализации чата.

Базовые категории:

- OpenAI-compatible Chat Completions — configurable base URL, API key, tool calls, SSE (например, OpenRouter, OpenAI-compatible self-hosted providers при совместимости).
- Anthropic Messages API — собственная схема сообщений/tools/usage.
- Gemini API — своя адаптация структуры входов и usage.
- OpenRouter — отдельный адаптер для каталога/маршрутизации, реальной стоимости, кеша, provider metadata.
- Другие поставщики — через плагины/адаптеры по реальным capabilities.

**Не обещать, что любой URL поддерживает любой инструмент.** Capabilities явно отражают: tools, parallel tool calls, text streaming, image input/output, reasoning controls, system role, max context, caching, usage, pricing, modality formats. При несовпадении UI и координатор показывают понятную причину.

### 5.2. Настройка подключения

- Несколько профилей провайдеров, названия, модели, endpoint, (опционально) дополнительные заголовки с безопасным allowlist.
- API-токены и пароли в Android Keystore / зашифрованной локальной обёртке; не в database plaintext, не в diagnostic, не в prompt/tool result.
- Проверить подключение; изолировать ошибки авторизации/нет сети/неподдерживаемая модель/нет средств/timeout.
- Возможность удалить профиль и токен.
- Не передавать личные данные новому провайдеру молча в рамках автоматического fallback.

### 5.3. Протокол

- События `onDelta`, `onToolCall`, `onUsage`, `onFinish`, `onError`, `onCancelled`.
- Потоки SSE и частичные tool calls собираются детерминированно, проверяются схемой и разрешениями.
- При нестабильной сети не дублировать оплаченный POST без обоснованной идемпотентности: отделить «восстановление результата» от «создать новый ответ».
- Ошибки и rate limits имеют backoff; пользователь видит, ждём ли результат, исправляем ошибку или задача приостановлена.

## 6. Обязательное кеширование и экономичное использование моделей

### 6.1. Главный принцип

**Prompt caching включено по умолчанию** там, где доступно и совместимо. Не существует одного универсального параметра, который включает кеш для любого API и любой модели. `CachePolicy` выбирает стратегию по реальным capabilities и документации поставщика; отсутствие поддержки не ломает запрос.

Различать:

1. **Provider prompt caching:** экономия на повторно читаемом префиксе запросов; основной приоритет.
2. **Локальное deterministic caching:** безопасные преобразования, статические правила, валидные tool schemas, повторные локальные операции, исключение платного polling; должен учитывать TTL/изменение данных.
3. **Response caching:** повтор готового модельного ответа — не включать автоматически в задачи с меняющимся внешним состоянием и побочными действиями.

### 6.2. Требования к контексту

- Системные правила, перечень базовых возможностей и исходный якорь задачи расположены стабильно: не переписывать начало prompt после каждого инструмента.
- Динамический прогресс передавать компактными типизированными событиями/сообщениями после стабильного префикса.
- Для поддерживаемых провайдеров ставить корректные `cache_control`/`prompt_cache_key`/`session_id`; проверять срок действия, порядок блоков и дополнительные расценки на cache write.
- Схемы всех сотен доступных инструментов **не вставлять в каждый запрос**: компактный каталог/поисковый selector → загрузка нужных схем, когда задача действительно предполагает вызов. Не прятать инструмент, необходимый для выполнения исходного задания.
- Результаты инструментов сокращать структурно: ошибки, существенные поля, ID ресурса, ссылки на артефакты. Длинные лог-файлы хранить локально, отдавать модели нужные фрагменты.
- Большие файлы передавать через `artifactId` в инструментальную шину, а не через пересылку текста/байтов каждый шаг.
- Не заставлять модель по кругу проверять GitHub Actions/страницу: локальное ожидание событий/таймер и одно итоговое резюме.
- Управление budget для reasoning и генерации — адаптивное, настраиваемое. Уменьшать бессмысленные десятки тысяч выходных токенов на простые операции; не обрывать сложные задачи только ради фиксированного числа шагов.

### 6.3. Прозрачная статистика

По **каждому модельному вызову** сохранять, где провайдер сообщил значения:

| Метрика | Содержание |
| --- | --- |
| `input_total` | Общий объём входных токенов; правила включения кеша зависят от поставщика |
| `input_uncached` | Фактически обработанный ввод без кеша |
| `cache_read` | Повторно прочитанные из кеша токены |
| `cache_write` | Созданные/записанные в кеш токены (могут иметь особую цену) |
| `output_total` | Сгенерированные токены, включая reasoning, если это семантика провайдера |
| `reasoning` | Отдельная доля внутренней генерации, если сообщается |
| `real_cost` | Сумма от провайдера; не выводить из собственной оценки при наличии точных данных |
| `estimated_cost` | Лишь явно обозначенная оценка для провайдера без точной суммы |
| `cache_hit_ratio` | Доля известных cache_read в сопоставимых input; неизвестное ≠ 0 |
| `provider/model/time` | Фактический маршрут, модель и длительность |

Считать итог по пользовательскому поручению **суммой всех завершённых платных вызовов** (включая дочерние задачи), с отдельными разбивками по chat, Browser, GitHub, Shell, служебным моделям; если часть calls неизвестна — показывать «неполные данные». Нельзя двойным счётом прибавлять cached к уже включающему их total input или reasoning к total output.

В меню **«Об ответе»** показывать минимум: модель, provider, длительность, вход обычный/кеш, запись в кеш, выход, reasoning, количество вызовов и фактическую стоимость. Историю статистики хранить локально, экспортировать без секретов. Для длительного агента отображать текущую известную стоимость и счётчик модели **по ходу** исполнения.

### 6.4. Критерий эффективности

Для типового тестового задания сравнить обычный многошаговый сценарий с оптимизированным при одной и той же модели: доля кешированных input, число повторных чтений, суммарные output/reasoning, реальная стоимость и процент выполненных задач. Улучшения допускаются только без потери результата/безопасности. Никаких обещаний «50 млн токенов за $3» как гарантированной цены: она зависит от маршрута, цен, структуры токенов, TTL и cache hit.

## 7. Единая шина инструментов: AgentToolBus

### 7.1. Что получает модель

Модель видит каталог **только доступных и разрешённых** инструментов с названиями и кратким назначением. При выборе получает JSON-схему аргументов и capability-описание. Tool details подгружаются по необходимости, чтобы не увеличивать каждый запрос.

Общий `ToolDescriptor` содержит:

- `id`, `version`, `name`, `description`, `inputSchema`, `outputSchema`;
- required permissions/capabilities, allowed resource classes, potential side effects;
- timeout, concurrency policy, cancellability, expected cost/runtime if known;
- поддерживаемые операции, создание/закрытие сессии и версии контракта.

Общий `ToolCall` содержит: `taskId`, `callId`, `toolId`, validated arguments, `grantId`, timeout, cancellation token. Общий `ToolResult` содержит: `status`, structured summary, `artifactIds`, resource refs, safe error code, actual effects, retry hint, elapsed time.

### 7.2. Правила связи

- Чат отправляет `UserIntent`; `AgentRunner` выбирает tools; `ToolDispatcher` проверяет схему/полномочия и вызывает адаптер.
- `ToolAdapter` не получает сырой ключ LLM/общий Vault и не видит все остальные подключения. Ему дают ограниченную ссылку `connectionId` и scoped доступ.
- Один инструмент не обращается к другому напрямую. Модель и координатор связывают шаги по typed results/`artifactId`.
- Число инструментов **не ограничено архитектурой**, но есть реальные лимиты CPU, памяти, активных подключений, окон модели и UI. Каталог выбирает нужное по задаче.
- Все tool calls сопровождаются событиями start/progress/finish/retry/cancel и оценкой локальных/связанных расходов.

### 7.3. Последовательные и параллельные действия

- План — граф задач (DAG), не одна гигантская блокирующая функция.
- Независимые чтения GitHub и Browser могут идти параллельно; создание файла после скачивания — только после готовности входного artifact ID.
- Per-tool concurrency: WebView одного таба сериализуется; независимые браузерные сессии ограничены ресурсами; SSH host имеет отдельные ограничения; сетевые вызовы — rate limits.
- Повтор только когда операция допускает safe retry/idempotency key. Не дублировать создание репозитория, коммит, оплату, отправку сообщения, установку ПО.
- При изменении/отмене первоначальной цели coordinator не оставляет бесконтрольные дочерние задачи.

### 7.4. Якорь задачи, checkpoint и полнота

- Хранить исходный запрос неизменно + версионируемые новые указания пользователя.
- Отдельно: критерий успешного конца, запреты, активный task, этапы, ссылки на созданные ресурсы и подтверждённые результаты.
- После каждого значимого шага атомарный checkpoint в локальное хранилище.
- При восстановлении после падения/обрыва сети проверять реальное состояние и продолжать; не запускать ту же платную/побочную операцию наугад.
- Конечный ответ обязан отличать `done`, `partially_done`, `failed`, `cancelled`. Фраза модели «готово» не заменяет проверку артефакта, CI или фактического состояния сайта.

## 8. Браузер — ключевой первоочередной инструмент

**Основной технический ориентир — лучшие открытые решения Android/агентного браузера.** Требуется не очередной простейший `WebView.loadUrl()`, а управляемая браузерная сессия с сочетанием доступного DOM и визуального действия.

### 8.1. Принцип гибридности

Браузер должен уметь сам выбирать дешёвый и надёжный способ:

1. **Структурный DOM/семантический снимок** — основной путь: интерактивные элементы с id/ref, ролью, текстом, visibility, bounding box и состоянием.
2. **Точный HTML/text extraction** — ограниченный объём нужных данных, без полного сырого DOM на каждый шаг.
3. **Визуальный fallback** — скриншот и координатные/элементные действия только если DOM-навигация недостаточна, сайт рендерится нестандартно или агенту действительно нужен визуальный контекст.
4. **Стабильные сценарии** — уже известную последовательность обычных действий исполнять локально и проверять результат, без модели на каждом клике; при изменении страницы вернуться к наблюдению/планированию.

### 8.2. Минимальный полный набор инструментов Browser

- `open/goto`, `back/forward`, `reload`, `close`, `tabs list/create/select/close`;
- `snapshot` семантического дерева + адрес/заголовок/состояние страницы;
- `read_text`/`extract` структурированного содержания по схеме;
- `click/tap`, `type`, `select`, `scroll`, `focus`, `keypress`, `submit` (в границах полномочий);
- `wait_for` по DOM/URL/тексту/состоянию сети/таймауту; учитывать динамическую загрузку;
- `screenshot`, точечные визуальные действия с привязкой координат к версии viewport;
- обработка HTML dialogs, file chooser, скачивания и загрузки файлов через общий ArtifactStore/SAF;
- сессии/cookies по origin, вход пользователя через takeover при необходимости, сохранение/закрытие своей сессии;
- контроль редиректов, всплывающих окон и открытия внешних приложений;
- ясный `element_not_found`, `stale_ref`, `ambiguous_target`, `navigation_failed`, `requires_user`, `blocked_by_policy` и другие структурные ошибки.

### 8.3. Безопасность Browser

- Каждая навигация и HTTP redirect проверяется по реальному URL, разрешённому origin и целевой сети; защита SSRF, localhost/LAN по политике, DNS rebinding и запрещённым schemes.
- Недоверенный JS/DOM/страница не расширяет permissions и не получает доступ к Android bridge, секретам, файловым путям и другим сессиям.
- Разрешить обычные клики/поиск/чтение без лишних подтверждений, но платежи, необратимые удаления, публикуемые формы, секреты и существенная отправка данных требуют risk gate по реальному действию.
- Капчи, вторую факторную авторизацию, оплату и интерактивный логин — через видимый ручной takeover; обход ограничений безопасности не реализовывать.
- Маскирование паролей, токенов, cookies и чувствительных полей в снимках, скриншотах, логах и ответах модели.
- Изолированные сессии и управляемое уничтожение локального состояния по команде пользователя.
- Ясные таймауты, cancellation и проверка `stale_ref` перед click/type.

### 8.4. Браузерные критерии приёмки

- Пройти минимум пять сайтов с различными шаблонами: классическая DOM-страница, SPA с динамической отрисовкой, страница с загрузкой файла, несколько вкладок, форма с подтверждением.
- Выполнить реальные цепочки `поиск → страница → извлечение → файл` без лишних вызовов модели и потери контекста.
- Проверить кнопку «Остановить», сеть offline/online, потерю Activity, закрытие вкладки и безопасное восстановление.
- Проверить prompt injection на страницах, приватный URL/redirect, UI редирект, iframe и stale элемент.
- Не признавать Android Browser полностью эквивалентным desktop Playwright/CDP без реальных тестов: ограничения WebView должны быть задокументированы.

## 9. Инструменты и плагины в первой и последующих версиях

### 9.1. Форматы расширений

- **Встроенные Android-адаптеры:** отдельные Gradle/Kotlin-модули, включённые в APK. Наиболее надёжны для WebView, файлов, диктовки, локального Shell, GitHub и SSH.
- **Внешние подключения:** API/MCP/HTTP-совместимые инструменты по протоколу и настройкам; при необходимости работают без пересборки APK. Их возможности получают такой же ToolDescriptor/TaskGrant/permission gate.
- **Скачиваемый исполняемый Android-код** не является обязательным вариантом расширения. Если когда-нибудь нужен, обсуждать отдельно подписи, provenance, API stability, изоляцию и политику безопасности. Не исполнять произвольный JS/Kotlin из каталога плагинов без подтверждённой архитектуры sandbox.

### 9.2. Первые реальные инструменты

1. Browser — первоочередной большой адаптер.
2. GitHub + GitHub Actions — операции с репозиторием и создание APK; вести отдельно от нового основного чата.
3. Локальные файлы — SAF, операции с файлами/архивами; общая ArtifactStore.
4. Local Shell — ограниченное исполняющее окружение, без скрытых root/ADB обходов.
5. SSH/SFTP — отдельные host-сессии, передача файлов, long-running jobs.
6. MCP/подключаемые API — адаптер для расширения, а не альтернативное агентное ядро.

Иные инструменты обсуждать позже по запросу пользователя. Не затягивать первую версию одновременной реализацией всех интеграций.

### 9.3. Примеры проверки независимости

- Добавить новую простую mock tool без изменений `ChatScreen` и `AgentRunner`.
- Удалить модуль GitHub из Gradle — базовый чат и Browser продолжают собираться.
- Провайдер без tool calling выдаёт корректную ошибку совместимости только при агентном запросе, не ломает обычный чат.
- GitHub и Browser выполняются одновременно; они не разделяют секреты и состояния.

## 10. События работы, статусы и наблюдаемость

### 10.1. Видимая панель агента

Компактный блок поверх или внутри ленты диалога, обновляемый **в реальном времени**, а не после финального ответа. Показывать:

- `Текущая задача` (обобщённая без секретов) и общее состояние;
- шаги «создал репозиторий», «читаю страницу», «ожидаю CI», «исправляю ошибку», «загружаю файл»;
- длительность активного этапа и подтверждённое число успешных/неуспешных операций;
- затраты по завершённым модельным вызовам и подсказку о неполном учёте;
- доступ к «Подробностям», остановке и видимому ручному действию при `WAITING_USER`.

**Запрещено имитировать внутренний chain-of-thought.** Показывать короткие подтверждённые действия, состояния, ошибки и пользовательский текст, а не приватные рассуждения модели.

### 10.2. Локальная диагностика

Структура событий `timestamp`, `taskId`, `toolId`, `requestId`, safe status/error code, duration, optional known token/cost. По умолчанию не писать: ключи, cookies, сырые сообщения чата, stdout/stderr, web HTML, содержимое файла, скриншоты. При экспорте дополнительно очищать чувствительные поля. Ошибки пользователя не должны превращаться в бесконечный дорогой LLM loop.

## 11. Модель безопасности и приватность

Базовые правила:

1. Разрешения исходят из прямого ввода пользователя и его явно включённых подключений, а не из документа/письма/сайта/ответа инструмента.
2. `PermissionGate` срабатывает **перед каждым фактическим побочным действием**, включая редиректы Browser, запись remote repo, отправку файла, запускаемую команду и установку APK.
3. Обычные промежуточные шаги поручения автоматические. Запрашивать подтверждение только для действий с существенными последствиями: платёж, публичная публикация, массовое/необратимое удаление, изменение доверия/секретов, опасная установка, значимые внешние отправки вне ранее согласованного адресата/содержания.
4. У каждого provider/tool своё connectionId с минимальными полномочиями. Отключение подключения немедленно блокирует новые вызовы.
5. Предусмотреть возможность остановить и стереть историю/артефакты; миграции БД и backup описать отдельно.
6. Вызовы модели могут раскрывать выбранному API-провайдеру необходимое содержимое поручения — это нужно отражать в настройках приватности; инструментальные секреты не раскрывать модели никогда.
7. Сетевые права/клиентские сертификаты/Android permissions и WebView security не обходить ради удобства.

## 12. Тестирование и критерии качества

### 12.1. Автоматические проверки

- `:core:contracts` — сериализация и обратная совместимость типов.
- `:core:agent` — завершение задачи по конечному критерию, ошибка/отмена/переход к следующему этапу.
- `:core:task` — DAG, параллельность, гонки, восстановление, идемпотентность.
- `:core:toolbus` — новый tool mock, schema validation, таймаут, ошибки, unauthorized.
- `:core:security` — prompt injection, elevation, redirection, secrets, forbidden side effects.
- `:core:provider` — обычный и streaming response, tool fragments, reasoning, usage, разные схемы provider.
- `:core:context` — стабильный prompt prefix, правильное кеширование по модели, отсутствие неподдерживаемых параметров, compaction.
- `:core:storage` — atomic checkpoints/migrations/large artifacts.
- `:tools:browser` — DOM, stale refs, redirects, scripted fixture pages, manual takeover.
- `:features:chat` — UI состояния/кнопки/длинные сообщения/клавиатура/прогресс.
- `:features:voice` — офлайн русский текст, разрешения и отмена.
- Android R8 release checks: символы reflection, JSON adapters, сохранение всех features.

### 12.2. Сквозные приёмочные сценарии

**A. Простой чат.** Добавить провайдера, получить потоковый ответ, копировать, озвучить, открыть «Об ответе», сменить шрифт/цвет и звук; после перезапуска история сохранена.

**B. Офлайн-диктовка.** Отключить сеть, произнести русский запрос, увидеть редактируемый текст в композере; ничего не отправлено без нажатия пользователя.

**C. Провайдеры.** Один и тот же сценарий текста пройти минимум на двух **разных** API-адаптерах, а не на двух моделях OpenRouter. Проверить недоступный tool calling, недействующий ключ, ошибки API и SSE.

**D. Кеш и расходы.** Несколько шагов одной задачи с тем же статичным system/tools prefix. Измерить реальные `cache_read`/cache write, output/reasoning и точную стоимость; не смешивать response-cache и prompt-cache. Проверить отсутствие поддерживаемого кеша и метрик.

**E. Browser.** Агент посещает сайт, находит информацию, использует структурный snapshot, при необходимости screenshot, скачивает файл, возвращает итог без данных cookie. После редиректа в запрещённую сеть операция блокируется.

**F. Комбинация инструментов.** Browser получает файл; Files проверяет; GitHub создаёт/обновляет тестовый репозиторий; один независимый этап параллелен другому. Тест проходит без импортов одного инструмента в другой.

**G. Идея → APK.** Пользователь просит простое Android-приложение; агент создаёт отдельный тестовый репозиторий и код, настраивает Actions, исправляет ошибку CI, скачивает/передаёт действительно существующий APK. Создание только README/workflow или зелёный CI без APK — провал.

**H. Прекращение и восстановление.** Отключение интернета, сворачивание приложения, отмена, повторный запуск Android. Никаких двойных платных вызовов и дублированных коммитов без подтверждения.

### 12.3. Порог приёмки этапа

Не принимать модуль, пока нет: исходников, unit+negative tests, зелёного fast CI, полного lint/debug/R8 CI (где применимо), реального Android-теста ключевого сценария, понятных UI состояний, исправления критических вопросов безопасности, обновления `docs/ROADMAP.md` в GitHub. Одинаково важно фиксировать «код готов» и «реально принят» как разные состояния.

**[Agentic WebView — `shanthropic/agentic-webview`](https://github.com/shanthropic/agentic-webview)** — наиболее непосредственно релевантный *Android SDK* ориентир: typed browser session, DOM refs, navigation policy, screenshots, structured errors, независимость от конкретной LLM. Проект сравнительно молодой; обязательно оценить стабильность и качество реальных тестов, не принимать SDK без ревизии security и Android совместимости.

**[Stagehand — `browserbase/stagehand`](https://github.com/browserbase/stagehand)** — идеи `act`/`observe`/`extract`, детерминированных процедур, кеширования проверенных действий и self-healing при изменении страниц. Это не нативный Android WebView SDK; оценивать концепции, не принуждать приложение к облачному браузеру.

### 13.2. Как именно заимствовать лучшее

Прежде чем выбрать компонент:

1. Зафиксировать commit SHA стороннего репозитория, лицензию и дату аудита.
2. Выписать полезные идеи и реальные ограничения Android/Android WebView.
3. Сравнить минимум 2 варианта реализации: готовая библиотека или самостоятельный маленький адаптер.
4. Проверить реальную архитектуру, наличие unit/Android tests, сопровождаемость, угрозы, размер зависимостей и API stability.
5. Составить ADR: решение, причины, риски, альтернативы, принятый вариант.
6. Не копировать чужой исходный код/ресурсы без отдельной проверки лицензии и уведомлений. Лицензия чужого проекта **не равна** разрешению переносить всё без выполнения условий. Особая осторожность с LGPL/GPL и производными файлами.
7. Если идея не подходит, не заставлять архитектуру повторять проект-источник.

### 13.3. Критерии выбора браузерной основы

Оценивать по шкале с измерениями: Android WebView совместимость, security architecture, отслеживание реального URL и redirects, качество DOM/refs, скриншоты и visual fallback, работа JS SPA, расход prompt/LLM calls, поддержка файлов/вкладок, защита секретов, отмена/восстановление, лицензия/поддержка/CI. Выбор исключительно по stars GitHub запрещён.

## 15. Нефункциональные требования

- Android на Kotlin + Jetpack Compose; актуальные стабильные Android SDK и Gradle выбираются в момент старта проекта.
- Kotlin Coroutines/Flow для состояния и асинхронности; cancellation должна работать через всю цепочку вызовов.
- DataStore для настроек, Room/SQLite для истории/задач, Android Keystore для секретов, SAF для внешних файлов.
- Жизненный цикл Android: foreground service/WorkManager лишь по назначению, без ложного обещания неограниченного фона.
- Accessibility: TalkBack, масштаб текста, контрастность, крупные touch targets.
- Диагностика без конфиденциальных данных, возможность экспортировать для исправления ошибок.
- CI по каждому PR, устойчивые сборки Debug и R8 Release; релизы — только по явному поручению.
- Не предъявлять искусственных ограничений размера APK; при этом измерять холодный старт, потребление RAM и зависания UI.
- Приложение может работать с любым провайдером, но отсутствие интернета для облачной LLM не должно ломать локальную диктовку, историю и ранее сохранённые файлы.

## 16. Definition of Done — финальная проверка архитектуры

Преобразование Umnik соответствует замыслу, когда одновременно верно:

- [ ] Чат может работать без всех tools и provider не прошит в UI.
- [ ] К одному агенту подключаются Browser и любой другой tool независимо; они могут работать последовательно/параллельно.
- [ ] Новая tool адаптация не требует переписывания чата и основного AgentRunner.
- [ ] Браузер управляет реальной страницей на Android в DOM + screenshot режимах и соблюдает runtime политики.
- [ ] Офлайн русская диктовка работает без сети и не отправляет текст автоматически.
- [ ] Пользователь настраивает цвет, шрифт и звук ответа.
- [ ] Под каждым ответом есть копирование, озвучивание, компактное меню дополнительных действий.
- [ ] В «Об ответе» есть токены и реальная стоимость, включая известные cache hit/write/reasoning и агрегат агентной задачи.
- [ ] Prompt caching используется по умолчанию у поддерживаемых провайдеров; нет фальшивых нулей и недопустимых опций API.
- [ ] Задача, прогресс, права и артефакты переживают паузу/перезапуск в пределах возможностей Android.
- [ ] Вмешательства человека требуются по реальному риску, а не на каждом безопасном шаге.
- [ ] Старые монолитные центры ответственности заменены независимыми модулями, нет циклических зависимостей, architecture tests/Android CI зелёные.
- [ ] Проведена инвентаризация Umnik, судьба удалённых функций явно утверждена, из работающей ветки доступен проверенный APK, старый `main` не изменён.
- [ ] Есть подтверждённые тестовые сценарии на телефоне; приложение возвращает конечный результат, а не промежуточное «готово».

**Остальные функции решаются позже отдельными ADR и поправками к этому документу, без неявного расширения из старых чатов.**
