# Проекты в Umnik

Проект - это рабочее пространство, где несколько ИИ-чатов могут выполнять разные роли, использовать общий контекст и взаимодействовать через ◆ Оркестратор.

## Из чего состоит проект

Проект может содержать:

- несколько специализированных чатов;
- ◆ Оркестратор;
- мастер-инструкцию проекта;
- общие файлы;
- общие навыки;
- общую базу знаний;
- общие последовательные этапы.

При этом каждый чат остаётся отдельным исполнителем со своим состоянием.

## Профиль отдельного чата

Для проектного чата можно закрепить:

- модель;
- reasoning;
- силу reasoning;
- веб-поиск;
- OpenRouter tools;
- навыки;
- постоянные файлы;
- базу знаний;
- роль;
- мастер-инструкцию;
- индивидуальные этапы;
- собственную историю сообщений.

Это позволяет создавать не просто «несколько вкладок», а устойчивые рабочие роли.

Например, чат «Редактор» не должен каждый раз заново получать инструкцию «проверяй текст, не переписывай его целиком». Его роль и рабочие настройки можно закрепить один раз.

## Общий и личный контекст

### Общий уровень проекта

Подходит для материалов, которые должны быть доступны всей команде:

- цель проекта;
- общие правила;
- техническое описание;
- общие документы;
- база знаний проекта;
- общий набор навыков.

### Личный уровень чата

Подходит для специализации:

- собственная роль;
- индивидуальная модель;
- личные файлы;
- собственная база знаний;
- отдельные навыки;
- история работы именно этого исполнителя.

Так проект может иметь общую предметную область, но разные профессиональные роли.

## Этапы проекта и этапы чата

В Umnik есть два уровня последовательных этапов.

### Этапы проекта

Общие для проекта. Подходят для повторяемого общего процесса.

Пример:

1. разобрать исходные материалы;
2. выделить факты;
3. подготовить решение;
4. проверить итог.

### Этапы конкретного чата

Принадлежат одному исполнителю.

Например, у чата «Автор» могут быть свои этапы:

1. составить структуру;
2. написать черновик;
3. сократить повторы;
4. выдать итог.

Этапы запускаются последовательно. Следующий этап получает результаты предыдущих.

## Когда использовать этапы, а когда Оркестратор

**Этапы** удобны, когда процесс известен заранее и повторяется одинаково.

**◆ Оркестратор** удобен, когда пользователь хочет описать нужную последовательность прямо во время работы обычным языком.

Например:

> Пусть Исследователь сначала проверит тему, потом Аналитик сравнит варианты, а Автор подготовит итог.

Это не требует заранее создавать отдельный постоянный сценарий.

Подробнее: [ORCHESTRATOR.md](ORCHESTRATOR.md).

## Файлы

В проекте есть несколько уровней файлового контекста.

### Файлы проекта

Постоянные материалы, доступные в проекте.

### Файлы конкретного чата

Материалы, которые относятся к одному исполнителю и должны оставаться у него между запросами.

### Разовые вложения

Используются для конкретного сообщения или запуска.

### Файлы результата

Модель может создать новый файл. Оркестратор способен передать такой результат другому чату проекта.

## Базы знаний

Для больших источников лучше использовать не обычные постоянные файлы, а RAG-базу знаний.

Можно иметь одновременно:

- общую базу проекта;
- отдельную базу Исследователя;
- отдельную базу Дизайнера;
- отдельную базу Редактора.

Подробнее: [KNOWLEDGE_BASE.md](KNOWLEDGE_BASE.md).

## Пример проекта «Редакция»

**Исследователь**

- веб-поиск;
- модель, хорошо работающая с фактами;
- инструкция искать первоисточники.

**Отборщик**

- более экономичная модель;
- задача фильтровать слабые темы.

**Автор**

- сильная текстовая модель;
- стилевой навык;
- свои примеры и книги в базе знаний.

**Редактор**

- reasoning;
- правила проверки;
- отдельная база знаний по редактуре.

**◆ Оркестратор**

- принимает поручение пользователя;
- запускает нужных участников;
- передаёт результаты и файлы;
- позволяет вернуть отдельный кусок на доработку.

## Пример проекта «Разработка приложения»

Можно создать роли:

- Архитектор;
- Разработчик;
- Ревьюер;
- UX;
- Исследователь документации.

А затем писать Оркестратору:

> Архитектор предложит решение. Исследователь проверит актуальную документацию. Результаты передай Разработчику, а его ответ - Ревьюеру.

Если нужно исправление:

> Передай замечания Ревьюера Разработчику и попроси исправить только найденные проблемы.

Так не приходится повторно запускать всю цепочку.

## Почему не один большой чат

Один длинный чат постепенно накапливает смешанные роли, устаревшие инструкции и лишний контекст.

Раздельные проектные чаты позволяют:

- держать историю по ролям;
- экономнее выбирать модели;
- включать дорогие инструменты только там, где они нужны;
- давать каждому исполнителю свою базу знаний;
- легче проверять промежуточные результаты;
- дорабатывать один участок процесса без повторения всей работы.

Именно поэтому проект в Umnik - это не папка с чатами, а небольшая управляемая ИИ-команда.
