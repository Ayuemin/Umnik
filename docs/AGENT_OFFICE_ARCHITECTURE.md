# Архитектурная концепция Umnik: офис независимых ИИ-агентов

Статус: зафиксированная целевая концепция для дальнейшей переработки проектов и Оркестратора.

## 1. Главная идея

Umnik должен строиться не вокруг «чатов проекта», а вокруг **независимых ИИ-агентов**.

Каждый агент — самостоятельная личность и фактически отдельное мини-приложение внутри проекта. У него нет общих с другими агентами настроек, навыков, памяти или базы знаний.

Единственное, что связывает агентов между собой, — **Оркестратор**, который ими управляет.

Проект при этом — только **помещение / кабинет**, где находятся Оркестратор и агенты. Проект не раздаёт им общие инструкции, навыки, модели, память или базы знаний.

---

## 2. Проект

Проект — минимальный контейнер:

```text
Проект
├── название
├── Оркестратор
├── Агент A
├── Агент B
├── Агент C
└── рабочие задания / сценарии
```

В проекте НЕ должно быть скрытого наследования:

- мастер-промпта проекта;
- общих навыков;
- общей базы знаний;
- общей модели;
- общего reasoning;
- общих инструментов;
- общей памяти.

Новый агент создаётся «голым», с безопасными техническими значениями по умолчанию.

---

## 3. Агент

Агент — отдельная сущность, а не просто `ChatSession`.

Целевая модель:

```text
AgentProfile
- id
- projectId
- name
- role
- instruction
- connection
- model
- reasoningEnabled
- reasoningEffort
- webSearch
- tools
- skills[]
- knowledgeBase[]
- files[]
- memorySettings
- stages[]
- createdAt
- updatedAt
```

Чат отделяется от личности агента:

```text
AgentConversation
- id
- agentId
- messages[]
- attachments[]
- createdAt
- updatedAt
```

Это позволяет в будущем иметь несколько разговоров с одним и тем же агентом без потери его личности и настроек.

### Принцип изоляции

Изменение любого параметра одного агента никогда не меняет другого агента.

Агент A не наследует от агента B:

- модель;
- уровень размышления;
- поиск;
- инструменты;
- навыки;
- файлы;
- память;
- базу знаний;
- этапы.

---

## 4. Навыки

Общая библиотека навыков не является частью целевой модели.

Каждый агент владеет своими навыками.

В настройках агента должны быть доступны:

- `+ Создать навык` — написать прямо в Umnik;
- `Загрузить файл`;
- `Загрузить папку`;
- редактировать;
- удалить.

Если нужен похожий навык у другого агента, можно позже добавить **«Скопировать навык из другого агента»**.

Копирование создаёт независимую копию. Дальнейшие изменения не синхронизируются.

---

## 5. База знаний и файлы

Каждый агент имеет свою изолированную базу знаний и свои файлы.

Даже если два агента используют одну и ту же книгу, логически это две независимые привязки.

Внутри хранилища допускается дедупликация по хэшу, чтобы не хранить одинаковый физический файл дважды, но это не должно создавать общую логическую библиотеку.

Пример:

```text
Аналитик -> книга X
Редактор -> книга X
```

Физически файл может быть один, но права доступа и индексы принадлежат каждому агенту отдельно.

---

## 6. Оркестратор

Оркестратор — особый агент и руководитель офиса.

У него есть свои независимые:

- инструкция;
- модель;
- reasoning;
- память;
- навыки;
- база знаний;
- инструменты.

Дополнительно он имеет право **управлять агентами проекта**.

Основные обязанности Оркестратора:

1. понять задачу пользователя;
2. определить план;
3. выбрать нужного агента;
4. поставить ему задачу;
5. решить, какие входные материалы передать;
6. оценить результат;
7. решить, кому и что передать дальше;
8. вернуть задачу на доработку при необходимости;
9. завершить работу и собрать итог.

Агенты не общаются друг с другом напрямую.

---

## 7. Диспетчер / «Курьер»

Чтобы Оркестратор не тратил модельные вызовы и внимание на техническую «беготню», вводится системный компонент **TaskDispatcher**.

Пользовательское рабочее название может быть «Курьер» или «Диспетчер».

Это НЕ ИИ-агент. Он не думает и не принимает решений.

Он исполняет решения Оркестратора:

```text
Оркестратор
   │ решение
   ▼
TaskDispatcher
   ├── находит нужного агента
   ├── собирает пакет задачи
   ├── запускает агента
   ├── ждёт результат
   ├── сохраняет результат
   ├── переносит файлы/артефакты
   ├── ведёт статус
   └── возвращает результат Оркестратору
```

### Пример команды Оркестратора

```text
CALL_AGENT
agent = researcher
objective = "Проверь факты"
inputs = [user_material, analyst_result]
expected_output = "список подтверждённых фактов"
```

Диспетчер выполняет команду технически и сообщает Оркестратору о завершении.

---

## 8. Пакет задачи агенту

Оркестратор передаёт агенту не чужую память и не чужую базу знаний, а **рабочий пакет текущего задания**.

Пример:

```text
AgentTaskPackage
- taskId
- agentId
- objective
- stageInstruction
- constraints
- inputResults[]
- inputFiles[]
- userMaterial[]
- expectedOutput
```

Агент использует этот пакет вместе со своими личными:

- инструкцией;
- навыками;
- базой знаний;
- памятью;
- моделью;
- инструментами.

---

## 9. Результат агента

Результат должен быть отдельным рабочим объектом:

```text
AgentResult
- resultId
- taskId
- agentId
- outputText
- files[]
- summary
- facts[]
- warnings[]
- createdAt
```

Оркестратор сам решает, что из результата передать следующему агенту:

- весь результат;
- краткую выжимку;
- отдельные файлы;
- только конкретные части.

Чужая личная история агента, его навыки и база знаний автоматически дальше не передаются.

---

## 10. Рабочее пространство задания

Для каждого большого задания существует отдельное временное рабочее пространство:

```text
JobWorkspace
├── исходная задача пользователя
├── план Оркестратора
├── пакеты агентам
├── результаты агентов
├── файлы текущей работы
├── журнал передачи результатов
└── итоговый результат
```

Это НЕ общая память проекта и НЕ база знаний агентов.

После завершения задания рабочая история может храниться для просмотра, но результаты не должны автоматически записываться в постоянную память всех участников.

---

## 11. Журнал обмена

Передача результатов должна быть наблюдаемой.

Пользователь должен иметь возможность открыть историю работы и увидеть:

```text
Оркестратор -> Аналитик
Аналитик -> Оркестратор
Оркестратор -> Исследователь
Исследователь -> Оркестратор
Оркестратор -> Автор
...
```

Для каждой передачи желательно видеть:

- кому;
- когда;
- какую задачу;
- какие материалы;
- какой результат;
- какие файлы;
- статус.

Это важно и для пользователя, и для диагностики Оркестратора.

---

## 12. Создание нового агента

UX:

```text
Проект -> + Новый агент -> Настройки агента
```

Экран агента сразу содержит все индивидуальные параметры.

Вверху:

`Перейти в чат без настройки`

После настройки:

`Сохранить и перейти в чат`

Новый агент НЕ наследует параметры предыдущего агента.

Допустимы только нейтральные технические значения по умолчанию, например:

- текущее рабочее подключение;
- текстовая модель по умолчанию;
- reasoning выключен;
- web search выключен;
- навыков нет;
- база знаний пуста;
- память пуста;
- этапов нет.

В будущем полезна команда **«Дублировать агента»**, создающая полностью независимую копию.

---

## 13. Local и Server

Архитектурная модель должна быть одинаковой в обоих режимах.

### Umnik Local

Всё выполняется на Android:

- агенты;
- их базы;
- память;
- Оркестратор;
- Диспетчер;
- OpenRouter-вызовы.

### Umnik Server

Полный Umnik живёт на VPS:

- агенты;
- базы;
- embeddings;
- рабочие задания;
- Оркестратор;
- TaskDispatcher;
- очередь выполнения;
- вызовы моделей.

Android / Web UI становятся клиентами.

Пользователь может закрыть интерфейс, а работа продолжится на VPS.

---

## 14. Ключевые инварианты

1. **Агент полностью независим от других агентов.**
2. **Проект ничего не наследует агентам.**
3. **Оркестратор — единственная управляющая связь между агентами.**
4. **TaskDispatcher исполняет технические действия, но не принимает смысловых решений.**
5. **Личные знания агентов не смешиваются.**
6. **Рабочие результаты передаются явно через Оркестратор.**
7. **Рабочее пространство задания не является общей постоянной памятью.**
8. **Новый агент создаётся с чистыми настройками.**
9. **Чат не является агентом; чат принадлежит агенту.**
10. **Одинаковая концепция должна работать и локально, и на VPS.**
11. **Повторное выполнение не должно незаметно повторять уже оплаченный запрос после неопределённого сетевого сбоя.**

---

## 15. Что это заменяет в текущей реализации

Текущая схема, где `ChatSession` одновременно играет роль специалиста, а проект хранит общие `skillIds` и часть общих настроек, считается переходной.

Целевое направление рефакторинга:

```text
ChatSession = разговор
AgentProfile = личность и рабочая среда специалиста
Project = кабинет
Orchestrator = руководитель
TaskDispatcher = исполнитель технических поручений
JobWorkspace = временное рабочее пространство задачи
```

Точечные исправления наследования навыков, reasoning и других параметров не должны закреплять старую модель. Приоритет — постепенный переход к этой архитектуре без поломки существующей стабильной версии.
