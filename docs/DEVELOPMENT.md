# Разработка Umnik

Этот документ — короткая карта проекта для следующего разработчика, ревьюера или нового рабочего чата. Если нужно продолжить работу после паузы, начните отсюда, затем смотрите `main`, последний релиз и актуальный CI.

## Источник истины

- `main` — единственная актуальная линия разработки.
- стабильные состояния сохраняются тегами `vX.Y.Z` и GitHub Releases;
- старые feature/fix/release/tmp-ветки не считаются актуальными сами по себе;
- перед продолжением любой старой ветки сначала сравните её с `main`;
- временные workflow и patch-скрипты не должны оставаться в `main`.

## Быстрая проверка проекта

Требования:

- JDK 17;
- Android SDK 37;
- Gradle 9.6.1.

Основная локальная проверка:

```bash
./gradlew --no-daemon :app:lintDebug :app:testDebugUnitTest :app:assembleDebug --stacktrace
```

Для публичного APK используйте только `.github/workflows/android-release.yml`: он собирает release APK постоянным ключом, проверяет подпись и публикует контрольную сумму.

## Карта ключевых файлов

### Чат и состояние

- `app/src/main/java/com/ayuemin/ymnik/ChatViewModel.kt` — основная координация UI, чатов и команд специалистов. Не добавляйте сюда новые хранилища или сетевые адаптеры без отдельного компонента.
- `app/src/main/java/com/ayuemin/ymnik/data/ChatRepository.kt` — хранение истории чатов. Для конкурентных изменений используйте атомарные операции `updateChat`/append, а не схему «прочитал весь список → изменил → сохранил» из нескольких корутин.
- `app/src/main/java/com/ayuemin/ymnik/ui/YmnikApp.kt` и `ui/NavigationSidebar.kt` — состояние текущего чата и индикация фоновой работы.

### Выполнение запросов

- `RequestExecutionManager.kt` — реестр активных верхнеуровневых запросов и резервирование рабочих чатов.
- `RequestNetworkSession.kt` — сетевые клиенты, принадлежащие одному верхнеуровневому requestId.
- `RequestConcurrencyLimiter.kt` — опциональный пользовательский лимит. Значение `0` означает отсутствие клиентского ограничения. Не вводите скрытый фиксированный предел.
- `RequestKeepAliveService.kt` — foreground-служба Android, которая живёт до завершения последнего активного запроса и показывает системное уведомление.
- `OpenRouterRecoveryWorker.kt` — безопасное восстановление прямого текстового запроса после смерти процесса/долгого сетевого обрыва.
- `network/OpenRouterRecoveryStore.kt` — временные локальные recovery-записи без plaintext API-ключа.
- `network/OpenRouterRecoveryPolicy.kt` — правила, когда replay через response cache вообще разрешён.
- `network/OpenRouterClient.kt` — сетевой вызов OpenRouter, Generation ID, response cache и отмена конкретного клиента.
- `network/OpenRouterRequestEnhancer.kt` — OpenRouter server tools и настройки конкретного чата.
- `network/OpenRouterChatBatchRunner.kt` — Batch в рамках конкретной сессии запроса.

### Команды и Оркестратор

- `docs/DOMAIN_TERMINOLOGY.md` — обязательные названия доменных сущностей и legacy-границы.

- `model/OrchestratorCodec.kt` и модели специалистов — протокол решений Оркестратора.
- `docs/ORCHESTRATOR.md` — пользовательская и техническая логика Оркестратора.
- `docs/TEAMS.md` — модель команд и разговоров специалистов.
- `docs/KNOWLEDGE_BASE.md` — RAG/база знаний.

## Инварианты параллельных запросов v1.17+

Эти правила считаются частью архитектуры и не должны случайно ломаться при следующих доработках.

1. В одном обычном чате одновременно выполняется не более одного верхнеуровневого запроса.
2. Разные чаты могут выполнять запросы параллельно. Umnik не должен искусственно делить их по 2/3/5 или вводить другой скрытый предел.
3. Каждый верхнеуровневый запрос имеет собственный `requestId`, отмену, таймер и сетевую сессию.
4. Результат всегда записывается в исходный чат, даже если пользователь уже открыл другой чат.
5. Stop в текущем чате отменяет работу этого чата, а не чужие параллельные запросы.
6. Foreground-служба остаётся активной, пока не завершился последний запрос.
7. Оркестратор обязан атомарно резервировать worker-чат на всё время поручения. Пока чат зарезервирован, ручной запрос в него не запускается.
8. Сетевой вызов исполнителя Оркестратора должен знать фактический `chatId` исполнителя (`network.call(chat.id)` или эквивалент), иначе server tools могут получить настройки не того чата.
9. `OpenRouterRequestEnhancer` не должен определять рабочий чат через старое глобальное состояние. Идентичность запроса/чата передаётся явно.
10. История чата при параллельных завершениях обновляется атомарно, чтобы один результат не перетёр другой.
11. Активный или зарезервированный чат нельзя удалить. Команду нельзя удалить, пока работает любой её разговор или Оркестратор.
12. Независимые действия Оркестратора можно запускать параллельно; действия, зависящие от предыдущего результата, остаются последовательными. Не возвращайте фиксированную группировку «по три».
13. Сетевой обрыв после получения Generation ID не должен автоматически превращаться в новый платный запрос: сначала проверяется уже существующая генерация OpenRouter и подтверждение response cache.
14. Recovery после смерти процесса разрешён только для прямого пользовательского текстового запроса; внутренние шаги Оркестратора не должны автономно дописываться worker-ом.
15. Recovery не хранит plaintext API-ключ. Повтор допускается только при совпадении SHA-256-отпечатка текущего ключа с исходным.
16. Ручной Stop окончателен: он удаляет recovery-запись, отменяет WorkManager и не позволяет фоновому worker позже доставить ответ.

## Чего избегать

- глобального `currentCall`/единственного mutable сетевого запроса на всё приложение;
- глобального `activeChatId` как источника истины для нескольких параллельных работ;
- чтения изменяемых настроек модели уже после старта запроса вместо snapshot при отправке;
- неатомарных полных перезаписей истории из конкурентных корутин;
- временных GitHub Actions workflow в `main`;
- изменения `applicationId` без отдельной миграции;
- коммита API-ключей, keystore и секретов.

## Порядок работы над изменением

1. Обновиться от `main` и убедиться, что CI зелёный.
2. Создать понятную ветку: `feature/...`, `fix/...`, `docs/...`.
3. Делать изменение одной логической задачей.
4. Перед PR выполнить `:app:lintDebug`, `:app:testDebugUnitTest` и `:app:assembleDebug`.
5. В PR описать пользовательский эффект и технические риски.
6. Исправить review-замечания и повторно прогнать штатный PR-CI.
7. После merge проверить push-CI уже на `main`.
8. После выпуска версии удалить/закрыть временные ветки и служебные workflow, если они больше не нужны.

## Возобновление работы после нового чата или долгой паузы

Проверяйте в таком порядке:

1. HEAD `main`;
2. последний GitHub Release и его тег;
3. последние Android CI/Android Release runs;
4. открытые PR;
5. только затем — незавершённые feature-ветки.

Если несколько экспериментальных веток решают одну задачу, не угадывайте «самую новую» по имени: сравните каждую с `main` по commit SHA и diff. После слияния итоговой реализации старые варианты больше не являются источником истины.

## Релиз

Полная инструкция: `docs/RELEASING.md`.

Коротко:

1. поднять `versionCode` и `versionName`;
2. обновить `CHANGELOG.md`;
3. получить зелёный PR-CI;
4. merge в `main` и дождаться зелёного push-CI;
5. создать точный тег `vX.Y.Z` на проверенном commit;
6. запустить `Android Release`;
7. убедиться, что опубликованы APK, `.sha256` и отпечаток постоянного сертификата.
