# ADR: команда как Оркестратор и независимые специалисты

Статус: принято 17.09.2026; терминология и совместимость обновлены 23.09.2026.

**Терминология:** текущая сущность называется **Команда**, её участники — **Специалисты**. Слова **Проект** и **Агент** зарезервированы для будущих сущностей. См. `DOMAIN_TERMINOLOGY.md`.

Этот документ дополняет `SPECIALIST_TEAM_ARCHITECTURE.md` и фиксирует решения, которые должны определять дальнейший рефакторинг Umnik.

## 1. Главная функция Umnik

Основной рабочий режим Umnik — **Команды**.

Команда — это кабинет, в котором находятся:

- Оркестратор;
- независимые специалисты;
- рабочие задания Оркестратора;
- TaskDispatcher (системный «Курьер»);
- журнал обмена результатами.

Команда не является источником общей личности, мастер-промпта, навыков, базы знаний, памяти, модели или reasoning для специалистов.

## 2. Простые чаты

Простые чаты остаются для обычного общения с моделью вне команд.

Они должны быть максимально простыми:

- разговор;
- модель;
- вложения;
- обычные параметры запроса;
- память/контекст, если пользователь её включает.

**Этапов в простых чатах нет.**

## 3. Этапы удаляются из архитектуры

Отдельная сущность «Этап» больше не нужна ни простому чату, ни новой модели команды.

Причина: если работе действительно требуется отдельная роль, инструкция, модель, знания или способ обработки материала, это должен быть **отдельный специалист**, а не очередной режим того же чата.

Пример старой модели:

```text
Чат автора
├── этап анализа
├── этап черновика
└── этап проверки
```

Целевая модель:

```text
Оркестратор
├── Аналитик
├── Автор
└── Контролёр
```

Каждый участник является полноценным независимым специалистом.

Если задача настолько проста, что отдельный специалист избыточен, Оркестратор может выполнить небольшое преобразование сам. Поэтому универсальный механизм этапов не нужен.

### Решение о совместимости

Переименование выполняется без потери уже созданных пользовательских данных.

Legacy-каталоги `projects` / `agents`, JSON-поля `projectId` / `agentId`, владельцы баз знаний и старые абсолютные пути читаются через совместимый слой и безопасно переносятся в новую схему. Старый механизм этапов при этом не возвращается в активную архитектуру.

## 4. Специалист

Специалист — самостоятельная сущность и не является `ChatSession`.

Новый специалист всегда создаётся с чистыми настройками. Он не наследует от последнего открытого чата или другого специалиста:

- роль;
- инструкцию;
- reasoning;
- reasoning effort;
- web search;
- инструменты;
- навыки;
- базу знаний;
- файлы;
- память;
- историю.

Допустимы только нейтральные технические значения, необходимые для первого запуска, например выбранное подключение и текстовая модель по умолчанию.

## 5. Навыки принадлежат специалисту

Глобальная библиотека навыков не является частью целевой модели.

Навык создаётся внутри конкретного специалиста и принадлежит ему. В интерфейсе специалиста должны быть:

- написать новый навык;
- загрузить файл;
- загрузить папку;
- редактировать;
- удалить.

Если в будущем понадобится перенос навыка между специалистами, это делается копированием, после которого обе копии независимы.

## 6. Оркестратор и TaskDispatcher

Оркестратор принимает смысловые решения:

- понимает задачу;
- выбирает специалиста;
- формулирует поручение;
- выбирает, какие результаты и файлы передать;
- оценивает ответ;
- решает следующий шаг;
- собирает итог.

TaskDispatcher ничего не решает. Он технически:

- формирует пакет;
- запускает специалиста;
- сохраняет результат;
- переносит выбранные результаты и файлы;
- ведёт статусы и журнал;
- возвращает результат Оркестратору.

Таким образом специалисты не имеют прямого доступа друг к другу.

## 7. Целевая структура

```text
Umnik
├── Простые чаты
│   └── обычный разговор
│
└── Команды
    └── Команда / кабинет
        ├── Оркестратор
        ├── Специалист A
        ├── Специалист B
        ├── Специалист C
        ├── TaskDispatcher
        └── JobWorkspace / журнал работы
```

## 8. Порядок перестройки

Перестройка выполняется по новой модели с обязательным сохранением пользовательских данных текущей реализации.

### Фаза A. Новый доменный слой

- `SpecialistProfile` как отдельная модель;
- `SpecialistRepository` как отдельное хранилище;
- индивидуальные настройки специалиста;
- связь разговоров с `specialistId`;
- никаких `stages` в специалисте.

### Фаза B. Новый интерфейс команды

- `+ Новый специалист` вместо создания «чата-специалиста»;
- после создания сразу открываются настройки специалиста;
- карточка специалиста содержит все индивидуальные параметры;
- отдельная кнопка для разговора со специалистом;
- Оркестратор отображается как особый специалист.

### Фаза C. Изолированные данные

- навыки специалиста;
- база знаний специалиста;
- файлы специалиста;
- память специалиста;
- при необходимости физическая дедупликация файлов без логического общего доступа.

### Фаза D. Оркестрация

- `SpecialistTaskPackage`;
- `SpecialistResult`;
- `JobWorkspace`;
- `TaskDispatcher`;
- журнал передачи результатов;
- вызов независимых специалистов Оркестратором.

### Фаза E. Удаление старой модели

После подключения нового интерфейса команды удалить:

- командные `ChatSession` как замену специалистам;
- legacy `project.skillIds` и старые общие настройки команды;
- старые этапы и редакторы этапов;
- старый сценарий Оркестратора, основанный на legacy `RUN_CHAT_STAGES` / `RUN_PROJECT_STAGES`;
- переходные функции исполнения этапов.

Старые пользовательские данные команды сохраняются через legacy-чтение и миграцию.

## 9. Инвариант разработки

Новые функции команды нельзя строить поверх предположения `ChatSession = специалист`.

Если для новой функции требуется личность специалиста, она должна работать через `SpecialistProfile` или следующий доменный слой новой архитектуры.

**Никакие новые функции не должны зависеть от механизма этапов.**


## 10. Инвариант оболочки: индикатор расходов

При перестройке главного экрана нельзя потерять компактный индикатор расходов в шапке.

Текущее полезное поведение сохраняется:

- индикатор показывает **общий расход по подключённому API-ключу**, а не стоимость конкретной модели, специалиста или команды;
- одно и то же значение показывается в обычных чатах, чатах специалистов и у Оркестратора;
- по нажатию открывается подробность по периодам: сегодня / неделя / месяц / всего по этому ключу;
- расходы разных моделей суммируются самим провайдером в usage одного API-ключа;
- отдельный счётчик стоимости специалиста, модели или JobWorkspace в текущей версии не нужен.

Umnik использует один OpenRouter API-ключ для обычных чатов и специалистов. В версии 1.19 мультиагрегаторность и собственный сервер исключены из продуктовой архитектуры, чтобы не поддерживать неиспользуемые параллельные контуры.
