## 1A. Общий «мост» AgentToolHub — ЧАСТИЧНО РЕАЛИЗОВАНО

**Статус (12.10.2026):** Registry, TaskGrant/ToolPermissionGate и dispatcher прошли CI. Guarded callbacks: `local_shell_status/stop`, Browser session control, `local_browser_open/read`. `ChatArtifactResolver` проверяет файл конкретного чата перед передачей в Shell (`b23f5dc`). Запуск Shell и прочие Browser callbacks пока не интегрированы полностью; нет TaskCoordinator и сквозной Android-приёмки. Не считать AgentToolHub завершённым.

**Цель:** все разрешённые инструменты доступны одному агенту в одном поручении;
агент может объединять их последовательно и выполнять независимые операции
параллельно. Новый инструмент присоединяется как стандартный адаптер, а
не дописывается в гигантский класс. Не начинать до приёмки диктовки.

- [ ] `ToolPermissionGate` — перед каждым реальным действием проверять

- [ ] `ArtifactStore` — безопасная передача файлов между инструментами по

**Этап подключения Browser Public Read (12.10.2026, подготовка):** `TrustedPublicBrowserReadGuard` и тип ресурса `PUBLIC_WEB_SESSION` задают **отдельную ограниченную возможность** для чтения публичного веба без URL в исходном запросе; выдача только на границе прямой UI-реплики при включённом Browser, с привязкой к чату, сообщению и сроку. Разрешены лишь open/read/scroll/wait/back — не click/type/download/execute. Проверка `checkActualPublicTarget` требует реальный адрес из runtime, валидирует схему/credentials/литеральный хост; DNS, redirect и непосредственный WebView enforcement остаются за runtime. **Пока grant не подключён к действующим callbacks и WebView**: не считать защиту включённой. Следующий шаг — связать API с реальным наблюдаемым URL на каждом переходе/редиректе без регрессии свободного публичного поиска и ручного `WAITING_USER`.

**Проверка текущего этапа:** быстрый CI `38286905014` (политика) и `38287476843` (реальные open/read) прошли успешно. Для приёмки обязательны полный Android CI (lint, unit tests, debug, R8 release) и затем отдельный APK-тест на Android: публичный поиск без URL; цепочка Google/CAPTCHA → другой поисковик → страница; чтение старой сессии из нового прямого запроса; проверка, что без grant/при истечении срока операции отклоняются. Не отмечать весь Browser/AgentToolHub завершённым до подключения callbacks, редиректов и подтверждения этого сценария на устройстве.

**Browser Public Read, первая рабочая интеграция (12.10.2026):** реальные `local_browser_open` и `local_browser_read` получают `PUBLIC_WEB_SESSION`-грант от доверенного `ChatViewModel.send`; обязательная проверка выполняется **внутри serialized Browser runtime**, до действия и после получения наблюдаемого URL WebView. Открытие/чтение без гранта блокируется. SSRF/DNS и SSL-проверки WebView остаются. **Это только два callbacks:** переходы через `click/type/back`, `scroll/wait`, редиректы на уровне `shouldInterceptRequest` и загрузка файлов пока не подключены к `TaskGrant`; нельзя считать Browser полностью защищённым. Требуется отдельная реализация atomic enforcement каждого реального target/redirect и Android-тесты.

**Сквозная передача артефактов (12.10.2026):** уже работающий Browser `persistBrowserDownload` переносит файл в `ChatFileRepository`, возвращает `chat_file_id`, а Local Shell выбирает файл из текущего чата по имени/ID. Новый `ChatArtifactResolver` валидирует локальный файл по ID и фактическому canonical path **в директории конкретного чата**, существованию, размеру и уникальности ID, прежде чем передать в Local Shell. Это безопасная основа будущего общего `ArtifactStore`, но **не** полноценный реестр/координатор и не разрешение на любые операции по ID. Следующий этап — типизированный доступ к file ID через общую шину; регрессия на реальном Android обязательна.

## 2. Визуальный Local Browser — ВТОРОЙ

- [ ] Сохранить существующий Chromium WebView, DOM-команды и защиту SSRF/SSL.
- [ ] Добавить получение скриншота текущей страницы / viewport по запросу модели только в рамках разрешённой сессии и с ограничением пикселей/стоимости.
- [ ] Маскировать пароль, OTP, платёжные данные и иные секреты ДО отправки картинки в OpenRouter; не передавать cookies.
- [ ] Комбинировать DOM + визуальный анализ для сложных сайтов, без слепых координатных кликов.
- [ ] Проверить точные действия и ограничения на новые окна, динамические элементы, iframe, shadow DOM и загрузки.
- [ ] Проверить безопасность и существующие `WAITING_USER`, загрузки, Fetch, AUTO/BROW/Поиск.
- [ ] Регрессионные тесты, CI, тестовый APK и проверка на Android.

## 3. Безопасный SSH/SFTP — ТРЕТИЙ

- [ ] Нативный Android SSH-клиент, без обязательной серверной части приложения.
- [ ] Список разрешённых SSH-хостов; проверка server host key, пользовательское подтверждение первичного подключения/изменения ключа.
- [ ] Секреты / приватные ключи в Android Keystore или платформенно подходящем зашифрованном хранилище, никогда в LLM.
- [ ] Сначала только команды чтения/диагностики. Уровни разрешений: чтение, изменение с подтверждением, запрет опасных команд.
- [ ] SFTP отправка/получение файлов и просмотр журналов.
- [ ] Строгие рамки task authority для каждой команды; недоверенный ответ сервера не может запустить новые действия.
- [ ] Лимиты времени/переданных данных, аудит без секретов, отмена операций, тесты в изолированном окружении.
- [ ] Не подключать к реальному VPS до полной проверки.

## 4. «Подключение агента» — ПЛАН, НЕ РЕАЛИЗОВАНО

**Единый раздел настроек** со списком подключений и тремя отдельными типами, с возможностью расширения. Не смешивать модельные провайдеры OpenRouter/Polza.ai с подключениями к внешним ресурсам:

- [ ] **Сайт / браузерная сессия:** название, канонический HTTPS origin, страница входа, ручная авторизация через WebView, сохранённые cookies. По желанию — логин и пароль только в защищённом локальном хранилище; CAPTCHA/OTP/SSO передаются пользователю.
- [ ] **API:** GitHub и другие сервисы через API-токен, PAT, OAuth (если поддерживается провайдером). Выбор конкретного API-коннектора и его URL/базового адреса, scope, разрешённых методов, лимитов; не создавать универсальную возможность произвольной отправки HTTP с секретом.
- [ ] **SSH / SFTP:** название хоста, hostname/IP, порт, имя пользователя, SSH private key + passphrase (опционально), при поддержке — парольная авторизация. Host-key pinning, предупреждение при изменении ключа сервера, отдельные read-only и mutation-разрешения, таймауты и ограничения на команды/файлы. Конфигурацию SSH не считать веб-сайтом.
- [ ] Для API-токена, пароля сайта, passphrase и приватного SSH-ключа использовать шифрованное локальное хранилище с защитой ключей через Android Keystore. **Никакие секреты не отправлять в OpenRouter, историю чата, tool result, MCP/LLM context, логи, скриншоты и файлы экспорта.** Агент получает только opaque connection ID и допустимые операции; конкретный секрет использует локальный адаптер.
- [ ] Пользователь явно включает каждое подключение и отдельно разрешает категории операций: чтение, скачивание, изменение, публикация, удаление. Новый подключённый сервис по умолчанию закрыт для агента до разрешения.
- [ ] API/SSH: для действий с побочными эффектами требовать подтверждение пользователя, не доверять произвольным командам из веб-страниц, кода, ответов серверов или tool output. Не давать LLM самостоятельно расширять scopes, изменять список разрешённых хостов или экспортировать креденшелы.
- [ ] Управление жизненным циклом: проверить соединение без выдачи секретов, отключить, отозвать токен/ключ, удалить запись, завершить браузерную сессию; эти операции не затрагивают остальные подключения.
- [ ] **Сайтовые загрузки:** авторизованный downloader с cookies только разрешённому origin, повторной проверкой каждого redirect, детектированием HTML вместо ожидаемого APK и сохранением через MediaStore / системный выбор Downloads; никакой автоматической установки APK.
- [ ] **MCP:** в будущем внешние инструменты могут ссылаться на connection ID, но не получать сырые пароли/токены/SSH-ключи. Ограничения и подтверждения проверяет основной runtime, а не модель.
- [ ] Тестовые сценарии: 4PDA login → скачать APK; GitHub API → прочитать issue/репозиторий с ограниченным токеном; SSH по ключу → прочитать логи; SFTP → скачать файл; запрет SSH-команд после prompt injection в логах и браузере.

**Порядок:** доработка этого раздела пока не начинается: сначала полный приёмочный цикл диктовки, затем визуальный Browser, затем безопасный SSH/SFTP. «Подключение агента» объединят готовые адаптеры и API-коннекторы отдельным последующим этапом.

Подробности для веб-сайтов: `docs/browser-accounts-and-safe-downloads.md`.

## 4A. Облачные диски: WebDAV и API — ПЛАН, НЕ РЕАЛИЗОВАНО

Это специализированные подключения внутри **Настройки → «Подключение агента» → «Облачные диски»**, а не открытие обычной страницы в браузере. Делать только после завершения предыдущих этапов.

- [ ] Универсальный файловый адаптер `CloudFilesConnector`: список папок, поиск по имени/пути, метаданные, получение файла в локальное хранилище чата, загрузка созданного в чате файла, создание папок. При ошибке возвращать реальный код/причину; не утверждать успешную доставку без ответа облака.
- [ ] WebDAV-адаптер для поддерживаемых сервисов (PROPFIND/GET/PUT/MKCOL; delete/move — только как отдельно разрешаемые операции). TLS, корректный URL encoding, таймауты и streaming для крупных файлов, без загрузки всего файла в оперативную память.
- [ ] **Яндекс Диск:** предпочтительно официальный REST API + OAuth с ограниченными правами; альтернативно WebDAV `https://webdav.yandex.ru`, пароль приложения «Файлы WebDAV». В документации Яндекса WebDAV указан как функция тарифов Яндекс 360 — проверять доступность у пользователя; учитывать, что удаление через WebDAV минует корзину.
- [ ] **Облако Mail.ru:** официальный WebDAV `https://webdav.cloud.mail.ru` с логином и отдельным паролем внешнего приложения (не основным паролем Mail). Возможность чтения/записи и ограничения тарифа проверять на реальном аккаунте.
- [ ] Не обобщать, будто каждый облачный сайт поддерживает API/WebDAV. Для остальных провайдеров — только если официально предоставлены интерфейс и разрешения; иначе ручной Browser-режим.
- [ ] Секреты и OAuth/WebDAV-пароли хранятся в защищённом локальном хранилище, никогда в LLM/OpenRouter, URL, логах или контексте инструментов. Адаптер принимает opaque connection ID и task scope, а не свободно сформированную моделью строку HTTP-запроса.
- [ ] Раздельные полномочия **поиск/чтение/скачивание** и **загрузка/перемещение/удаление**. Перед отправкой файла в облако показывать имя, размер и точный путь назначения, получить пользовательское подтверждение; никогда не принимать новое назначение/отправку из текста самого документа.
- [ ] Безопасный выбор источника созданного файла из текущего чата (реальный generatedFiles/storedFiles), проверка существования, путь назначения, конфликт имён, атомарность/повторяемость, подтверждение загрузки по метаданным облака.
- [ ] При скачивании хранить источник, оригинальное имя/тип/размер и локальный путь; не передавать содержимое документа внешней LLM без отдельного разрешения пользователя на обработку документа через OpenRouter.
- [ ] Автотесты и ручные сценарии: найти документ на Яндекс Диске → скачать → прочитать локально; сгенерировать TXT/DOCX/XLSX в чате → загрузить в Облако Mail; плохой пароль, просроченный OAuth, отсутствие подписки, прерванная связь, неверное расширение, конфликт имён, вредоносные подсказки в файле.
- [ ] Никакой фоновой синхронизации или зеркалирования всего облака без отдельной прямой задачи и разрешения пользователя.

Официальная документация:
- Яндекс Диск REST API: https://yandex.ru/dev/disk/rest/
- Яндекс Диск WebDAV: https://yandex.ru/support/yandex-360/customers/disk/web/ru/webdav
- Облако Mail WebDAV: https://help.mail.ru/cloud/desktop/webdav/

## 5. Агентная работа с Obsidian — ВАЖНО, только через общие файловые инструменты

**Точное требование пользователя:** не писать специальный «Обсидиан» внутри «Умника», не делать свой редактор заметок, интерфейс деревьев или настройки Obsidian ради простых действий. Пользователь может редактировать заметки в Obsidian вручную. Главная цель — **ИИ-агент по прямой голосовой/текстовой команде** самостоятельно создаёт и структурирует заметки.

- [ ] Минимально необходимый доступ: пользователь однократно выбирает каталог своего Obsidian vault (если он доступен приложению через Android Storage Access Framework / разрешённый общий каталог). Подключение — общее для файлов, не особый API Obsidian.
- [ ] Агент через существующие/расширенные инструменты Local Shell/файлового доступа читает, создаёт и редактирует обычные Markdown .md файлы и каталоги в рамках одного разрешённого vault; не нарушать scoped storage Android. Альтернатива только при реальной необходимости — URI команды Obsidian / внешний MCP-коннектор, но **не встраивать отдельную сложную интеграцию заранее**.
- [ ] Сценарий простой диктовки: «Запиши идею для статьи про Android в заметки» → локальное распознавание → пользователь отправляет текст → агент определяет смысл, путь и заголовок, создаёт .md файл → Obsidian видит изменение. Не требуется кодить свой интерфейс заметок.
- [ ] Сценарий организации: «Разложи заметки по темам, свяжи схожие записи и сделай оглавление» → агент читает содержимое, предлагает план изменений, сохраняет backup/журнал, создаёт папки, перемещает файлы и обновляет wiki/Markdown-ссылки по поручению пользователя.
- [ ] Агент самостоятельно выбирает структуру и исполняет промежуточные **разрешённые** файловые операции; содержимое существующей заметки не является новой командой и не повышает привилегии. Массовые перемещения/удаления требуют отдельного подтверждения.
- [ ] Проверять коллизии имён, экранирование путей, обход каталога (path traversal), битые ссылки, конфликт параллельного редактирования, отсутствие прав на каталог, восстановление из резервной копии. Не создавать дубли.
- [ ] Тест на копии vault: 10–20 заметок → голосовая задача → AI создаёт 1–2 заметки и ссылки; затем обрабатывает папки и обновляет индексы без потерь.

**Важно:** Obsidian здесь — приложение для просмотра/редактирования обычных заметок. Интеллектуальные действия выполняет модель с общими локальными инструментами «Умника». Никакой самостоятельной интеграции Obsidian в APK, если достаточно имеющегося доступа к файлам. Начать с малого после завершения текущих приоритетных задач.

## 6. Дополнительные внешние инструменты — ОЧЕРЕДЬ ПОСЛЕ ОСНОВНЫХ ЭТАПОВ

Сначала завершить диктовку, визуальный браузер, SSH/SFTP и безопасный каркас «Подключение агента». Затем внедрять по одному или объединять **только маленькие независимые** задачи при наличии общей проверки. Не создавать сразу десятки пунктов меню.

**Небольшие / можно объединять в компактные итерации:**
- [ ] Android Intents / SAF: открыть файл в другом приложении, разрешённая передача созданных файлов, доступ к выбранным папкам.
- [ ] RSS/Atom и GitHub Releases: читать источники, фильтровать дубликаты, собирать краткие подборки по прямому поручению.
- [ ] Obsidian/Markdown agent workflow на базе общего файлового инструмента (см. раздел 5) — без отдельного Obsidian-интерфейса.
- [ ] Календарь и напоминания через Android/официальные сервисные API при явных разрешениях; не добавлять событий без прямого поручения.
- [ ] Уведомления/проверка состояния разрешённых сервисов, только по команде или созданному пользователем расписанию.

**Крупные / тестировать отдельно:**
- [ ] GitHub API + Actions: read/diagnose, подготовка изменений в ветке, запуск CI, загрузка APK из артефактов с подтверждением операций записи.
- [ ] Почта IMAP/SMTP или официальный OAuth/API: чтение, вложения и черновики, отправка только после подтверждения.
- [ ] Windows / SMB / NAS: доступ к разрешённым каталогам, чтение/запись, проверка путей и полномочий.
- [ ] Базы данных: read-only запросы в первую очередь, только параметризованные и ограниченные запросы, отдельные права на запись.
- [ ] Webhooks / n8n: только зарегистрированные сценарии с ограниченными аргументами, никакого произвольного HTTP-execute.
- [ ] Home Assistant: только разрешённые сущности/операции; чувствительные действия подтверждать.
- [ ] Termux: внешний доверенный инструмент с allowlist, а не полный неограниченный shell и без обхода Android permissions.
- [ ] Общий MCP-клиент: проверка манифеста, permissions, provenance и запрет передачи секретов инструментам.
- [ ] Полноценные периодические задания и мониторинг: пользовательский schedule как отдельное подписанное полномочие, отмена и ограничения.

**Необязательная хотелка — самонастройка «Умника» агентом (низкий приоритет, после основных инструментов):**

- [ ] По **прямой голосовой или текстовой команде пользователя** агент может менять разрешённые настройки самого приложения: тему, размер шрифта, звук уведомлений, параметры отображения и другие безопасные пользовательские предпочтения.
- [ ] Не давать модели произвольный доступ к настройкам или файлам конфигурации. Использовать небольшой `AppSettingsTool` через общую шину `AgentToolHub`, поверх **существующих валидируемых API/репозиториев настроек**; каждый параметр — в явном allowlist с допустимыми значениями.
- [ ] Перед изменением проверять `TaskGrant` и показывать понятное «было → станет»; по возможности поддержать отмену последнего изменения. Параметры, влияющие на расходы, безопасность или сохранённые данные, требуют отдельного подтверждения.
- [ ] Запретить агенту самостоятельно изменять или раскрывать API-ключи, пароли, SSH-секреты, права подключений, системные разрешения Android, политики безопасности или список разрешённых инструментов. Внешние тексты/страницы/файлы не могут отдавать команды на изменение настроек.
- [ ] Реализовать только при небольшой сложности после приоритетных этапов и с отдельными тестами; **не делать большой рефакторинг или новое меню ради этой функции**. Пример: «Умник, переключи на тёмную тему и отключи звук готового ответа».

**Запрет:** не превращать Android-only «Умник» в обязательный клиент собственного сервера. OpenRouter остаётся единственным провайдером LLM; внешние сервисы подключаются только как инструменты, а не как замена модели.

## 7. Расширяемые плагины/MCP — ПОЗЖЕ

- [ ] Определить общий интерфейс внутренних и внешних инструментов, единый origin/task authority.
- [ ] При подключении нового инструмента права не выдаются автоматически.
- [ ] Обособленные настройки и отзыв разрешений на каждый инструмент/хост.
- [ ] Тесты против цепочек команд, исходящих от внешних источников.

## 8. Обязательные улучшения суммаризации и непрерывности длинных чатов — ПРИОРИТЕТНОЕ ТРЕБОВАНИЕ

**Решение пользователя (12.10.2026): выполнить ОБЯЗАТЕЛЬНО все три пункта.** Это не факультативная идея. **Очередность реализации определить позднее**; пока не привязывать к Browser, Shell, SSH или релизному циклу. За основу оставить текущую гибридную память Umnik (карточка состояния + checkpoint-конспекты + смысловой поиск по архиву). Код Operit AI использовать только как технический ориентир, не копировать.

- [ ] **Триггер сжатия по количеству реплик.** В режимах «Баланс» и «Эконом» добавить независимый от токенного порога, настраиваемый порог числа **новых завершённых ходов пользователя после последнего checkpoint/суммаризации** (ориентир из Operit — 16, окончательный умолчательный порог выбрать при реализации). При достижении порога обновлять накопительный конспект/карточку состояния; не пересуммировать без необходимости весь чат. Не учитывать неотправленные, прерванные и технические/tool-сообщения как новые пользовательские ходы. Исходная история всегда сохраняется. Проверить повторные запуски, конкурирующие запросы, переключение чатов и граничные значения.
- [ ] **Автоматическое восстановление после переполнения контекстного окна.** Определять ошибки провайдера/модели, действительно указывающие на превышение контекста; безопасно сокращать именно контекст запроса (суммаризация и сохранение актуальных инструкций/состояния), затем **ограниченно повторять** исходный запрос без необходимости ручной пересылки. Не путать ошибку контекста с авторизацией, сетью или лимитом денег. Исключить циклические повторные запросы, потерю текущего текста/вложений, повторное выполнение побочных действий инструментов, удвоение отправок/загрузок, раскрытие секретов и неожиданный рост расходов. При неудаче показать понятную ошибку и сохранить исходное сообщение.
- [ ] **Сжатие контекста внутри одной долгой агентной задачи.** В цикле AgentToolHub учитывать общий расход окна моделью, включая Browser/Shell и будущие tools. ## 9. ОБЯЗАТЕЛЬНО: автономность агента без лишних подтверждений — приоритет UX

**Решение пользователя (12.10.2026):** один прямой запрос пользователя разрешает агенту самостоятельно выполнять **все обычные промежуточные шаги** в пределах поручения, без отдельного подтверждения каждого инструмента или перехода. Это обязательный принцип для существующих Browser/Shell и будущих SSH, SFTP, GitHub, облаков, почты, MCP, файлов и Android-интеграций. **Порядок реализации определить отдельно.** Идею трёх уровней `ALLOW / ASK / FORBID` из Operit использовать только как концептуальную подсказку, чужой код не копировать.

- [ ] **По умолчанию — автоматическое продолжение:** чтение/поиск, обычная веб-навигация, безопасные клики/ввод, промежуточные вычисления, локальные файлы в разрешённой песочнице, подготовка/проверка/упаковка артефактов, создание и редактирование явно запрошенных локальных результатов, безопасные скачивания из разрешённых источников, естественные продолжения длинной задачи. Не делать отдельную модалку на каждый шаг. Не выдавать универсальный сетевой/Shell-доступ: операция обязана соответствовать `TaskGrant` и проверенному реальному ресурсу.
- [ ] **Автономный жизненный цикл сессий:** агент может запускать разрешённые инструменты, поддерживать несколько последовательных шагов и **самостоятельно завершать собственную Browser/Shell/SSH-сессию** или отменять собственную дочернюю задачу. Штатное завершение Local Shell уже автоматически выполняет runtime. Запрещено самостоятельно останавливать чужую/независимую задачу, даже если она в том же чате. Ручные кнопки «Стоп» доступны пользователю независимо от грантов модели.
- [ ] **Подтверждение только для существенных рисков:** деньги, покупка/оплата/финансовое обязательство; необратимое либо массовое удаление и опасная перезапись, особенно на серверах или в облаках; выдача/пересылка секретов и приватных данных третьим сторонам; выдача новых системных прав/изменение границ доступа, доверие новому SSH host key или изменённому ключу; установка ПО/APK; публичная публикация, отправка сообщений или файлов вовне без заранее явно согласованного адресата и содержания; другие труднообратимые последствия. Если прямое поручение уже однозначно разрешает конкретную безопасную операцию, не спрашивать повторно за её технические подшаги.
- [ ] **Browser — снизить ложные запросы подтверждения:** `local_browser_done` завершает свою сессию автоматически; `takeover`/ `WAITING_USER` применять только когда реально нужен человек (пароль, OTP, CAPTCHA, системный выбор файла, чувствительное подтверждение), не как обязательный этап навигации. Сегодня `clickScript` подтверждает многие *неизвестные* клики, а `typeScript` — практически любой POST: пересмотреть классификацию на основании достоверного эффекта и риска, **не ослабляя** защиту оплат/удаления/секретов. Проверять redirects и фактический URL внутри WebView.
- [ ] **Гранты не являются безусловным ALLOW:** решение об обычном автоматическом действии принимается по проверенным `TaskGrant` + реальным целям + риску операции. Текст страницы, API, файла, логов, заметки, вывода Shell или самой модели не может повысить права или отключить подтверждения. Никаких маркеров из аргументов инструмента для обхода gate; нельзя использовать найденный в Operit обход по `deny_tool`.
- [ ] **Проверки удобства и безопасности:** одна задача из 10–20 шагов Browser→файл→Shell→облако без постоянных вопросов; автоматическое завершение своих сессий; невозможность остановить чужой task ID; обычные действия проходят без подтверждений, а оплата, удаление, отправка секрета и изменение хоста блокируются до явного согласия; prompt injection не меняет разрешения. Быстрый и полный CI, тест на устройстве перед закрытием этапа.

### Универсальная адаптивная глубина работы агента — добавить при развитии AgentToolHub

**Принцип:** настройка поведения для **любого поручения**, а не отдельный промпт под веб-поиск, обзор приложений, сравнения или конкретный инструмент. Агент самостоятельно выбирает глубину исследования и исполнения, исходя из цели пользователя, сложности, неопределённости, последствий ошибки, имеющихся доказательств, цены и задержки. Слова «быстро», «кратко», «подробно», «проверь тщательно» из прямого запроса учитываются, но не расширяют права инструментов. По умолчанию не добавлять обязательный выбор режима и лишние элементы интерфейса.

**Архитектурное решение владельца (12.10.2026): основная модель — самодостаточный агент.** Она сама планирует, использует инструменты, оценивает полноту, обнаруживает пробелы и решает, продолжать или завершать поручение. **Не** вводить обязательного контролёра, диспетчера качества или второго LLM-«ревьюера» на базе системной модели: ни после каждого шага, ни перед каждым финальным ответом. Системная модель остаётся отдельным **служебным** исполнителем для уже предусмотренных задач (память/checkpoint, подготовка поисковых запросов к базе знаний, ограниченная диагностика зависших процессов Shell), не подменяя решения основной. Статусы инструментов, факты завершения, ограничения `TaskGrant`, ресурсные лимиты и подтверждения опасных действий проверяются детерминированным runtime `AgentToolHub`; это защита, не LLM-надзор. Новые вызовы системной модели в контуре агента не считать необходимыми для качества/автономности.\n\n- [ ] **Универсальная политика достаточности:** перед исполнением выявлять ожидаемый результат и критерии успеха; по мере работы оценивать, что уже достоверно установлено, что является допущением, какие существенные пробелы/противоречия остались и требуется ли ещё один шаг. Завершать только когда результат достаточен для данного запроса либо честно сообщать о нерешённых ограничениях. Не выдавать ранний удобный ответ за проверенный.
- [ ] **Глубина по задаче, а не жёсткие квоты:** не устанавливать универсально обязательное количество сайтов, источников, вызовов, токенов или минут. Простые, однозначные запросы решать быстро; сложные, неоднозначные или критичные задачи проверять тщательнее. Разные независимые свидетельства, первоисточники и перепроверка изменчивых фактов — средства снижения неопределённости **когда они уместны**, а не обязательный ритуал.
- [ ] **Один подход для всех инструментов:** Browser, Shell, локальные файлы, будущие SSH/SFTP, GitHub, облака, почта и API подчиняются одной политике качества и остановки. Оценивать не только найденные сведения, но и фактическое выполнение, корректность артефактов, статусы операций, завершённость шагов, ошибки и риски. `PageSnapshot.state=loading` или неполный вывод инструмента — сигнал проверить достаточность результата, но **не** автоматическое требование бесконечно ждать.
- [ ] **Управление расходами и прогрессом:** на каждом дополнительном шаге учитывать вероятную пользу, стоимость, задержку и ограниченность бюджета; прекращать повторяющиеся действия без нового результата, но не обрывать задачу только потому, что найден первый правдоподобный ответ. Если бюджет или доступ исчерпан, вернуть лучший проверенный частичный результат с явными пробелами, а не выдумывать полноту.
- [ ] **Непрерывность и безопасность:** хранить структуру цели, критериев готовности, доказательств и нерешённых вопросов в состоянии `TaskCoordinator` с передачей через сжатие контекста (раздел 8). Ни новый источник, ни внешний текст, ни «нужна более глубокая проверка» не расширяют `TaskGrant` или лимиты побочных действий; подтверждения только по риску (раздел 9).
- [ ] **Приёмка без привязки к примеру:** тестировать короткие и многоэтапные поручения разных классов (объяснение, поиск факта, исследование, преобразование файлов, проверка кода, несколько инструментов), неполные/противоречивые данные, недогруженные страницы, сбой инструмента, повторяющиеся шаги и ограниченный бюджет. Сравнить точность/полноту, ненужные tool-вызовы, стоимость, задержку и сохранение разрешений до и после; CI и реальный Android.

**Статус:** только согласованное требование к будущей общей политике агента; никаких изменений системного промпта, модели, настроек пользователей или runtime пока не сделано. Частный сценарий первого Browser smoke-test ниже — лишь регрессионный пример, не правило поведения.

### Правило релиза
Никаких утверждений «готово» до зелёных GitHub Actions и испытаний на устройстве. Тестовые сборки из work-ветки устанавливаются отдельно от стабильного «Умника». `main` не изменять.

### Режимы Android CI для ускорения работы

- **Обычный push в `work/**`:** быстрый CI — `:app:testDebugUnitTest :app:assembleDebug`, проверка Vosk в APK, публикация отдельного debug-артефакта. Это **не** подтверждение прохождения lint и R8.
- **Контрольный push в `work/**`:** добавить в сообщение коммита маркер `[full ci]`. Тогда выполняется исходный полный цикл `:app:lintDebug :app:testDebugUnitTest :app:assembleDebug :app:assembleRelease` с R8, проверкой Vosk и APK-артефактом.
- **Push в `main` и pull request в `main`:** полный цикл автоматически.
- **После завершения каждого функционального этапа** обязательно подтверждать зелёный полный CI перед испытанием на реальном Android или следующей крупной интеграцией. «Зелёный быстрый» не заменяет «зелёный полный».
- Для Gradle включён build cache и запись branch-scoped кеша в `work/**`. Не отключать тесты, R8 и проверки безопасности в контрольных сборках.
- Существующие подписанные релизы, F-Droid и стабильная `main` этой настройкой не изменяются.
