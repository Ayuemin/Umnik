# AgentToolHub — единая шина инструментов Умника

**Статус:** утверждённая целевая архитектура; реализация ещё не начата.
**Приоритет:** сначала завершить офлайн-диктовку и её тестирование, затем
постепенно внедрять общую шину, не прекращая последовательную разработку
Browser, SSH и остальных интеграций. Никаких изменений стабильной main.

## Замысел

Пользователь ставит ОДНО прямое поручение голосом или текстом; агент видит
каталог разрешённых возможностей и сам связывает шаги: Browser скачивает файл
→ локальный инструмент проверяет → Яндекс Диск загружает. Независимые операции
разрешено выполнять параллельно; зависимые ждут проверенного результата.

«Общий мост» не означает общую память секретов или прямые вызовы инструментов
друг к другу. Инструменты изолированы друг от друга по правам и жизненному
циклу. **Связь обеспечивается центральным координатором и типизированными
результатами**; недоверенный результат инструмента — только данные.

## Состав: несколько компактных компонентов, а не один огромный класс

| Компонент | Ответственность |
| --- | --- |
| `AgentToolHub` | Маленький фасад: получить доступные инструменты, маршрутизировать вызов по ID задачи |
| `ToolRegistry` | Регистрация `ToolDescriptor` и адаптеров, обнаружение возможностей |
| `TaskCoordinator` | План зависимостей, очереди, параллельные jobs, повторы, отмена, возобновление |
| `ToolPermissionGate` | Проверка исходного прямого поручения и разрешённых ресурсов перед каждым вызовом |
| `ArtifactStore` | Общий реестр локальных артефактов; передача file ID вместо сырых путей/байтов в промпте |
| `ToolSessionManager` | Изоляция браузерных и SSH-сессий, лимиты на параллельность по инструменту |
| `ToolExecutionLog` | Короткая диагностика состояний, затрат и ошибок без паролей, cookies и токенов |
| `ToolAdapter` | Небольшой независимый интерфейс к конкретному инструменту: Browser, Shell, GitHub, облако, SSH и т.д. |

Подход НЕ создаёт единого «суперкласса» на тысячи строк. Новые реализации
поставляются отдельными файлами/пакетами и регистрируются на общей шине.
Ориентир из `AGENTS.md`: 200–500 строк на файл, с обоснованными исключениями.

## Контракт инструмента

Каждый адаптер объявляет:
- устойчивый ID, краткое описание, версию, валидируемую схему параметров;
- требуемые разрешения (read, download, upload, write, delete, execute),
  типы ресурсов (HTTPS origins, каталоги, SSH hosts, API service/account);
- побочные эффекты и необходимость отдельного подтверждения;
- допущенную конкурентность (например, один WebView serial; отдельные SSH
  процессы parallel при разрешении и ресурсных лимитах);
- оценку срока, таймаут, отмену, состояние задачи, прогресс;
- типизированный результат: статус, безопасное резюме, artifact IDs,
  код ошибки, информация о фактическом побочном действии.

Реализация `ToolAdapter.execute(context, args)` не получает общий vault с
секретами. Использует только локальный сервис авторизации по ограниченному
connection ID. Результат никогда не содержит API ключи, SSH private keys,
cookies, пароли и т. п.

## Многошаговые сценарии

Пример А: пользователь «Найди на 4PDA APK и положи в Яндекс Диск»:
1. Создать `TaskGrant` из **прямого** сообщения пользователя, разрешённые
   цели: чтение/скачивание с указанного сайта, чтение скачанного файла и
   загрузка в выбранную папку облака; права имеют срок и область действия.
2. Browser ищет, при необходимости переходит в `WAITING_USER` для входа.
3. Файл сохраняется как `artifactId` с размером, MIME, SHA-256, provenance.
4. Опциональная локальная проверка файла.
5. `CloudFilesConnector` получает `artifactId`, загружает в согласованную
   папку, подтверждает итог по ответу сервиса. **Не устанавливать APK.**
6. Агент показывает реальный результат и причины неполного выполнения.

Пример Б: «Запусти SSH проверку; пока она идёт, изучи обновления GitHub»:
- SSH-адаптер запускает долгую операцию и выдаёт `jobId`; она не блокирует
  задачи чтения GitHub. Android хранит состояние и получает прогресс.
- После завершения обеих ветвей координатор объединяет результат.
- Независимые шаги параллельны, зависимые последовательно согласованы.
- Для длительных SSH-команд нужен серверный process/session lifecycle;
  обрыв Android не должен ошибочно считаться успешным выполнением команды.

Пример В: Obsidian:
- Без собственного редактора Obsidian. Общий локальный файловый адаптер с
  разрешением на выбранный vault даёт чтение/создание Markdown, папок,
  индексов и связей. Структуру выбирает агент, изменения ограничены vault.
- Перестройка/перемещение множества файлов — подтверждение и backup.

## Строгая безопасность

- Источник полномочий — только новый прямой ввод человека в поле чата
  (в том числе исправленный пользователем результат локальной диктовки),
  либо явно включённая и ограниченная пользователем запланированная задача.
- Browser DOM/скриншот, письмо, OCR, ZIP, Markdown, PDF, stdout/stderr, ответ
  внешнего API и любое сообщение модели **не могут расширять TaskGrant**.
- `ToolPermissionGate` вызывается **непосредственно перед каждым реальным
  побочным действием**, включая каждое действие в цепочке, а не лишь когда
  LLM планирует задачу.
- Новое подключение само по себе не создаёт доступа агента. Права
  определяются отдельно для конкретного пользователя, ресурса и задачи.
- Публикация, отправка сообщений/файлов вовне, удаление, установка APK,
  неочевидные изменения, выполнение привилегированной команды требуют
  отдельного доверенного подтверждения на устройстве.
- Обязательны ограничения числа параллельных операций, времени, размера
  файлов, расходов OpenRouter, количества повторов и возможности отмены.
- Ни одна модель не должна получать универсальный доступ к токенам/API/SSH.

## ОБЯЗАТЕЛЬНО: автономное исполнение и пропорциональные подтверждения

Пользователь подтвердил 12.10.2026: агент получает **одно прямое поручение** и самостоятельно завершает цепочку обычных действий без модальных вопросов на каждый технический шаг. Это применяется ко всем текущим и будущим инструментам.

- **Auto:** чтение, навигация, обычные UI-действия, безопасные загрузки, поиск, преобразование/сохранение локальных результатов в пределах выбранных файлов и папок, завершение собственных сессий, отмена только своего дочернего task ID. Никакого избыточного `WAITING_USER`.
- **Ask:** платёж, покупка, удаление/массовая перезапись, публичная публикация, отправка наружу без явно заданного адресата и содержания, опасная установка ПО, секреты и существенные изменения доступа/хост-ключей. Незаметное действие с высокими последствиями не становится безопасным потому, что это `click` или `EXECUTE`.
- **Forbid:** выход за рамки `TaskGrant`, чужие задачи/чаты, обход SSRF/SSL, утечки паролей и ключей, команды из недоверенного содержимого. Любой `ALLOW` обязан проверять фактический runtime ресурс; никаких строковых маркеров bypass.
- `local_browser_done` уже означает только `READY_TO_FINISH` без ручного подтверждения; `local_browser_takeover` фактически вызывает `WAITING_USER` и должен использоваться только при настоящем человеческом действии. В `clickScript` неизвестные элементы сегодня часто требуют подтверждения, в `typeScript` POST-формы считаются чувствительными; настроить точнее по уровню риска, сохранив запреты оплат/удалений/секретов.
- Local Shell завершается по штатному завершению worker. Отдельный `local_shell_stop` допустим для своей дочерней задачи и по прямому запросу пользователя; связь владельца с task ID проверяется в runtime. Ручная кнопка отмены остаётся доступной пользователю.
- Не копировать Operit. Изучен `PermissionLevel(ALLOW,ASK,FORBID)`; выявлен небезопасный текстовый обход `deny_tool` в его `ToolExecutionManager` — **не воспроизводить**.

Практические критерии приёмки — в разделе 9 `docs/WORKPLAN_voice-browser-ssh.md`. Выполнение этого правила пока не означает завершённую интеграцию `AgentToolHub`.
