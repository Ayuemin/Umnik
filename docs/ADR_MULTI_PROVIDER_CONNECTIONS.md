# ADR: общие подключения и мультиагрегаторная архитектура Umnik

Статус: принято 17.09.2026.

Этот документ дополняет `AGENT_OFFICE_ARCHITECTURE.md` и `ADR_AGENT_PROJECT_REBUILD.md`.

## 1. Решение

Umnik проектируется как **мультиагрегаторное / мультипровайдерное приложение**.

API-подключения принадлежат всему приложению, а не отдельным агентам.

Пользователь один раз настраивает подключение и API-ключ, после чего любое количество простых чатов, агентов и Оркестратор могут использовать это подключение.

Пример:

```text
Umnik
├── Подключения
│   ├── OpenRouter
│   ├── NVIDIA NIM
│   ├── OpenAI-compatible A
│   ├── OpenAI-compatible B
│   └── Umnik Server
│
└── Проект
    ├── Оркестратор -> connectionProfileId=openrouter -> model X
    ├── Аналитик     -> connectionProfileId=openrouter -> model Y
    ├── Исследователь-> connectionProfileId=nvidia     -> model Z
    └── Автор        -> connectionProfileId=custom-a   -> model Q
```

## 2. API-ключи

API-ключ не является частью личности агента.

Секрет хранится один раз в защищённом хранилище Umnik внутри профиля подключения.

Агент хранит только ссылку на подключение и выбранную модель:

```text
connectionProfileId
modelId
```

Изменение API-ключа в общих настройках подключения автоматически применяется ко всем агентам и чатам, которые используют этот профиль.

Нельзя требовать от пользователя повторно вводить один и тот же API-ключ при создании каждого агента.

## 3. Независимость агента не нарушается

Общими являются только технические ресурсы приложения:

- профили подключения;
- секреты/API-ключи;
- системный сетевой режим;
- локальный или серверный транспорт.

Индивидуальными остаются свойства агента:

- имя и роль;
- инструкция/личность;
- выбранное подключение;
- выбранная модель;
- reasoning и его параметры;
- поиск;
- инструменты;
- навыки;
- файлы;
- база знаний;
- память;
- история разговоров.

То есть два агента могут использовать один OpenRouter API-ключ, но оставаться полностью независимыми личностями.

## 4. Создание нового агента

При создании нового агента Umnik не спрашивает API-ключ.

По умолчанию агент получает текущее основное подключение приложения и текстовую модель по умолчанию. Пользователь меняет подключение только при необходимости.

Пример UX:

```text
Подключение: OpenRouter
Модель: anthropic/...
```

Если пользователь уже настроил OpenRouter, никаких дополнительных секретов в карточке агента вводить не нужно.

## 5. Возможности подключения и модели

Нельзя считать все провайдеры и модели одинаковыми.

Профиль подключения и каталог моделей должны описывать доступные возможности, например:

```text
text
imageGeneration
webSearch
reasoning
tools
embeddings
audio
video
```

Интерфейс агента должен показывать только совместимые параметры.

Примеры:

- если модель не поддерживает reasoning, соответствующая настройка не предлагается;
- если провайдер не поддерживает изображения, генерация изображений не включается;
- если инструменты недоступны, они не должны выглядеть как рабочие переключатели.

## 6. Оркестратор и TaskDispatcher

Оркестратор не обязан знать технические детали API конкретного провайдера.

Он выбирает агента для работы.

`TaskDispatcher` загружает `AgentProfile`, определяет его `connectionProfileId` и `modelId`, затем вызывает соответствующий адаптер провайдера.

Таким образом один проект может одновременно использовать агентов разных провайдеров без изменения логики Оркестратора.

## 7. Провайдерный слой

Целевая схема:

```text
AgentProfile
    ↓
connectionProfileId + modelId
    ↓
ProviderRegistry / ProviderAdapter
    ├── OpenRouterAdapter
    ├── NvidiaAdapter
    ├── OpenAiCompatibleAdapter
    └── будущие адаптеры
```

Оркестратор, агентная модель, память, навыки и JobWorkspace не должны зависеть от конкретного агрегатора.

## 8. Резервные маршруты

В будущем профиль или агент может иметь резервное подключение, но автоматическое переключение обязано соблюдать главный инвариант Umnik:

**после неопределённого результата уже отправленного платного POST нельзя молча повторять запрос через другого провайдера.**

Сначала должна использоваться безопасная проверка/восстановление состояния запроса. Резервный маршрут допустим до фактической отправки или после подтверждённого терминального отказа, когда дублирование исключено.

## 9. Local и Server

Та же модель используется и в локальном, и в серверном режиме.

В Local профили подключений и секреты находятся на устройстве.

В Server профили и секреты принадлежат личному серверу пользователя, а Android-клиент выбирает уже настроенные подключения через серверный API.

Архитектура агентов не должна меняться при переключении Local/Server.

## 10. Инварианты

1. API-ключ вводится один раз на профиль подключения, а не на агента.
2. Агент хранит ссылку на подключение, а не секрет.
3. Один проект может использовать агентов разных провайдеров.
4. Оркестратор не зависит от конкретного агрегатора.
5. TaskDispatcher выбирает нужный provider adapter по профилю агента.
6. Возможности UI определяются реальными capability провайдера/модели.
7. Добавление нового провайдера не должно требовать переделки `AgentProfile`, Оркестратора или JobWorkspace.
8. Безопасность от повторного платного POST важнее автоматического failover.
