# ADR: мультипровайдерные модели без глобального управления агентами

Статус: принято 17.09.2026, уточнено 18.09.2026.

Этот документ дополняет `AGENT_OFFICE_ARCHITECTURE.md` и `ADR_AGENT_PROJECT_REBUILD.md`.

## 0. Текущий этап реализации

Мультиагрегаторность является **архитектурным запасом на будущее**, а не частью первого нового тестового APK.

На текущем этапе:

- используется один общий OpenRouter API-ключ для всего Umnik;
- обычные чаты, Оркестратор и все агенты используют этот же ключ;
- пользователь выбирает модели внутри агента, но не настраивает отдельные API-подключения для каждого агента;
- индикатор расходов показывает общий usage этого API-ключа и не делится по моделям, агентам или проектам;
- UI выбора разных провайдеров внутри агентов пока не реализуется.

Внутренние модели данных могут оставаться готовыми к будущим разным провайдерам, если это не усложняет текущий интерфейс и не создаёт скрытого поведения.

## 1. Жёсткая граница общих настроек и агентов

Общие настройки Umnik управляют:

- обычными чатами «поболтать»;
- техническими профилями подключений и API-ключами;
- сетевым режимом Local / Server;
- настройками интерфейса приложения.

Общие настройки **не управляют агентами проекта**.

Из общих настроек нельзя:

- поменять модель агента;
- поменять его быстрые модели;
- поменять context-модель;
- поменять embeddings-модель;
- поменять embeddings-модель его базы знаний;
- включить или выключить reasoning;
- поменять навыки, память, файлы или базу знаний агента.

Агент настраивается только из собственной карточки внутри проекта.

## 2. Подключения — только техническая инфраструктура

API-ключи и профили подключения принадлежат приложению, чтобы пользователь не вводил один и тот же ключ многократно.

Примеры:

```text
Подключения Umnik
├── OpenRouter
├── NVIDIA NIM
├── OpenAI-compatible A
└── Umnik Server
```

Профиль подключения содержит технические данные и секрет.

Сам агент секрет не хранит.

## 3. Не «подключение агента», а ссылки на конкретные модели

Агент может использовать несколько моделей, причём они могут находиться у разных провайдеров.

Поэтому базовый тип:

```text
AgentModelRef
- connectionProfileId
- modelId
```

Внутри агента независимо хранятся:

```text
primaryModel
quickModels[]
contextModel
memoryEmbeddingModel
knowledgeBase.embeddingModel
```

Пример:

```text
Исследователь
├── основная модель      -> OpenRouter / Claude
├── быстрая модель       -> NVIDIA / Llama
├── context-модель       -> OpenRouter / Gemini
├── embeddings памяти    -> provider A / embedding-X
└── база знаний
    └── embeddings       -> provider B / embedding-Y
```

Это не нарушает изоляцию агента: профили подключений общие технически, но выбор моделей является частью конкретного агента.

## 4. Обычные чаты имеют свои глобальные defaults

Для режима «просто поболтать» общие настройки могут содержать:

- основную текстовую модель;
- быстрые модели;
- context-модель;
- embeddings-модель;
- reasoning и другие defaults обычного чата.

Эти значения относятся **только к простым чатам**.

Новый агент не наследует их автоматически.

Новый агент создаётся с пустыми модельными слотами и должен быть настроен внутри проекта.

## 5. База знаний принадлежит агенту

База знаний является частью локального рабочего пространства конкретного агента.

Она имеет собственную embeddings-модель:

```text
AgentKnowledgeBaseProfile
- enabled
- embeddingModel
- topK
- index metadata
```

Embeddings-модель базы знаний не обязана совпадать с embeddings-моделью памяти агента.

При смене embeddings-модели базы знаний индекс должен быть явно перестроен. Нельзя незаметно смешивать в одном индексе вектора разных моделей.

## 6. Локальное хранилище живёт вместе с агентом

Каждый агент имеет собственный корень хранилища:

```text
agents/<agentId>/
├── profile
├── conversations/
├── skills/
├── files/
├── knowledge/
├── memory/
└── generated/
```

Удаление агента удаляет его локальное рабочее пространство целиком, если пользователь не выбрал экспорт/архивирование.

Физическая дедупликация одинаковых файлов допустима только как внутренняя оптимизация. Логически данные остаются собственностью конкретного агента.

## 7. Оркестратор

Оркестратор тоже имеет собственные модели, память, навыки и базу знаний.

Но его специальные полномочия не связаны с провайдерами.

Он должен уметь:

- видеть список доступных агентов проекта и их публичные рабочие роли;
- выбрать агента;
- поставить ему задачу;
- передать выбранные результаты и файлы;
- запустить нескольких агентов параллельно, когда это уместно;
- получить результаты;
- сравнить результаты;
- отправить работу на доработку тому же или другому агенту;
- изменить план выполнения;
- пропустить ненужного агента;
- отменить ещё не выполненное поручение;
- собрать финальный результат;
- завершить JobWorkspace.

Оркестратор **не должен** менять постоянные настройки другого агента: модель, skills, reasoning, память или базу знаний. Он управляет работой, а не переписывает личность сотрудника.

## 8. TaskDispatcher

TaskDispatcher получает от Оркестратора только смысловое поручение и ссылки на рабочие материалы.

Для запуска агента Dispatcher:

1. загружает AgentProfile;
2. выбирает нужный model slot;
3. по AgentModelRef находит provider adapter;
4. подмешивает только личные данные этого агента и явно переданный рабочий пакет;
5. выполняет запрос;
6. сохраняет результат;
7. возвращает его Оркестратору.

Оркестратор не обязан знать API-формат конкретного поставщика.

## 9. Инварианты

1. API-ключ вводится один раз на техническое подключение.
2. Общие настройки чатов не достигают агентов.
3. Новый агент ничего не наследует от обычных чатов.
4. Каждый model slot агента содержит собственный AgentModelRef.
5. Модели одного агента могут использовать разных провайдеров.
6. Хранилище, навыки, память и база знаний принадлежат конкретному агенту.
7. База знаний имеет собственную embeddings-модель и собственный индекс.
8. Оркестратор управляет задачами, но не переписывает настройки агентов.
9. TaskDispatcher скрывает технические различия провайдеров.
10. После неопределённого платного POST запрещён молчаливый повтор через другой маршрут.
