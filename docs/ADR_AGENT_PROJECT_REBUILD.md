# ADR: проекты как офис независимых агентов

Статус: принято 17.09.2026, уточнено после тестирования 1.18.0.

Этот документ дополняет `AGENT_OFFICE_ARCHITECTURE.md` и фиксирует решения, которые должны определять дальнейший рефакторинг Umnik.

## 1. Главная функция Umnik

Основной рабочий режим Umnik — **Проекты**.

Проект — это кабинет, в котором находятся:

- Оркестратор;
- независимые агенты;
- рабочие задания Оркестратора;
- TaskDispatcher (системный «Курьер»);
- журнал обмена результатами.

Проект не является источником общей личности, мастер-промпта, навыков, базы знаний, памяти, модели или reasoning для агентов.

## 2. Простые чаты

Простые чаты остаются для обычного общения с моделью вне проектов.

Они должны быть максимально простыми:

- разговор;
- модель;
- вложения;
- обычные параметры запроса;
- память/контекст, если пользователь её включает.

**Этапов в простых чатах нет.**

## 3. Этапы удаляются из архитектуры

Отдельная сущность «Этап» больше не нужна ни простому чату, ни новой модели проекта.

Причина: если работе действительно требуется отдельная роль, инструкция, модель, знания или способ обработки материала, это должен быть **отдельный агент**, а не очередной режим того же чата.

Пример старой модели:

```text
Чат автора
├── этап анализа
├── этап черновика
└── этап проверки
```

Целевая модель:

```text
Оркестратор
├── Аналитик
├── Автор
└── Контролёр
```

Каждый участник является полноценным независимым агентом.

Если задача настолько проста, что отдельный агент избыточен, Оркестратор может выполнить небольшое преобразование сам. Поэтому универсальный механизм этапов не нужен.

### Решение о совместимости

На этапе текущей разработки обратная совместимость со старыми проектами **не является требованием**. Приложение пока тестируется ограниченно, и допустима чистая переустановка с новым форматом данных.

Поэтому разрешён breaking change:

1. удалить `ProjectStage` и связанные поля `stages` из целевой модели;
2. удалить UI создания, редактирования и запуска этапов;
3. удалить исполнение `runChatStages`, `runProjectStages` и связанные маршруты Оркестратора после перевода его на вызов агентов;
4. не писать миграцию старых этапов;
5. при необходимости изменить версию локального формата данных и начать проекты новой архитектуры с чистого состояния.

Важно: удаление должно быть **согласованным**. Нельзя оставить полуработающий старый механизм только ради того, чтобы старая база открывалась.

## 4. Агент

Агент — самостоятельная сущность и не является `ChatSession`.

Новый агент всегда создаётся с чистыми настройками. Он не наследует от последнего открытого чата или другого агента:

- роль;
- инструкцию;
- reasoning;
- reasoning effort;
- web search;
- инструменты;
- навыки;
- базу знаний;
- файлы;
- память;
- историю.

Допустимы только нейтральные технические значения, необходимые для первого запуска, например выбранное подключение и текстовая модель по умолчанию.

## 5. Навыки принадлежат агенту

Глобальная библиотека навыков не является частью целевой модели.

Навык создаётся внутри конкретного агента и принадлежит ему. В интерфейсе агента должны быть:

- написать новый навык;
- загрузить файл;
- загрузить папку;
- редактировать;
- удалить.

Если в будущем понадобится перенос навыка между агентами, это делается копированием, после которого обе копии независимы.

## 6. Оркестратор и TaskDispatcher

Оркестратор принимает смысловые решения:

- понимает задачу;
- выбирает агента;
- формулирует поручение;
- выбирает, какие результаты и файлы передать;
- оценивает ответ;
- решает следующий шаг;
- собирает итог.

TaskDispatcher ничего не решает. Он технически:

- формирует пакет;
- запускает агента;
- сохраняет результат;
- переносит выбранные результаты и файлы;
- ведёт статусы и журнал;
- возвращает результат Оркестратору.

Таким образом агенты не имеют прямого доступа друг к другу.

## 7. Целевая структура

```text
Umnik
├── Простые чаты
│   └── обычный разговор
│
└── Проекты
    └── Проект / кабинет
        ├── Оркестратор
        ├── Агент A
        ├── Агент B
        ├── Агент C
        ├── TaskDispatcher
        └── JobWorkspace / журнал работы
```

## 8. Порядок перестройки

Перестройка выполняется по новой модели, без обязанности сохранять старый формат проектов.

### Фаза A. Новый доменный слой

- `AgentProfile` как отдельная модель;
- `AgentRepository` как отдельное хранилище;
- индивидуальные настройки агента;
- связь разговоров с `agentId`;
- никаких `stages` в агенте.

### Фаза B. Новый интерфейс проекта

- `+ Новый агент` вместо создания «чата-специалиста»;
- после создания сразу открываются настройки агента;
- карточка агента содержит все индивидуальные параметры;
- отдельная кнопка для разговора с агентом;
- Оркестратор отображается как особый агент.

### Фаза C. Изолированные данные

- навыки агента;
- база знаний агента;
- файлы агента;
- память агента;
- при необходимости физическая дедупликация файлов без логического общего доступа.

### Фаза D. Оркестрация

- `AgentTaskPackage`;
- `AgentResult`;
- `JobWorkspace`;
- `TaskDispatcher`;
- журнал передачи результатов;
- вызов независимых агентов Оркестратором.

### Фаза E. Удаление старой модели

После подключения нового интерфейса проекта удалить:

- проектные `ChatSession` как замену агентам;
- общие `project.skillIds` и общие настройки проекта;
- старые этапы и редакторы этапов;
- старый сценарий Оркестратора, основанный на `RUN_CHAT_STAGES` / `RUN_PROJECT_STAGES`;
- переходные функции исполнения этапов.

Старые пользовательские проекты могут быть отброшены; миграция не обязательна.

## 9. Инвариант разработки

Новые функции проекта нельзя строить поверх предположения `ChatSession = агент`.

Если для новой функции требуется личность специалиста, она должна работать через `AgentProfile` или следующий доменный слой новой архитектуры.

**Никакие новые функции не должны зависеть от механизма этапов.**


## 10. Инвариант оболочки: индикатор расходов

При перестройке главного экрана нельзя потерять компактный индикатор расходов в шапке.

Текущее полезное поведение сохраняется:

- в обычном чате показывается расход активного подключения;
- по нажатию открывается подробность по периодам, если провайдер умеет отдавать такие данные;
- в чате агента индикатор связан с подключением его основной модели, а не с глобальными defaults обычных чатов;
- для Оркестратора дополнительно допускается отдельная стоимость текущего JobWorkspace, потому что одна задача может использовать несколько агентов и провайдеров.

Отсутствие usage API у конкретного провайдера не должно ломать шапку: индикатор либо скрывается, либо показывает локально рассчитанную стоимость, если она надёжно известна.
