# Umnik Personal Server

Экспериментальная серверная часть для Umnik. Она предназначена для **одного владельца** и не является многопользовательским сервисом.

## Зачем она нужна

Android может оборвать длинное соединение, когда приложение уходит в фон или экран гаснет. В серверном режиме телефон только создаёт задачу и затем читает её состояние. Сам запрос к OpenRouter выполняется на VPS и не зависит от жизненного цикла Android-приложения.

Ключевое правило: сервер не делает автоматический повтор `POST` к OpenRouter после сетевой ошибки. Это снижает риск второй оплаты за уже принятый провайдером запрос.

## Протокол v1

- `GET /health` — доступность сервера.
- `GET /v1/capabilities` — возможности протокола, требуется Bearer-токен.
- `POST /v1/chat/jobs` — создать долговечную задачу.
- `GET /v1/chat/jobs/{id}` — получить состояние или готовый ответ.

`client_request_id` уникален. Если телефон повторно отправит тот же ID с тем же payload, сервер вернёт уже существующую задачу и не создаст второй запрос к OpenRouter. Если тот же ID пришёл с другим payload, сервер ответит `409`.

## Быстрый локальный запуск

Создайте `.env` рядом с `compose.yaml`:

```env
OPENROUTER_API_KEY=sk-or-...
UMNIK_SERVER_TOKEN=случайная-длинная-строка
```

Затем:

```bash
docker compose up -d --build
```

По умолчанию Compose публикует порт только на `127.0.0.1:8787`. Для доступа из интернета перед сервером нужен HTTPS reverse proxy (например, Caddy или Nginx). Не публикуйте `8787` напрямую без TLS.

## Хранение

Состояние задач хранится в SQLite в volume `umnik-data`. После перезапуска незавершённая задача помечается как failed: сервер не пытается повторить оплачиваемый запрос автоматически.

## Пока не реализовано

- автоматическое развёртывание с телефона по SSH;
- интерфейс настроек в APK;
- отправка обычного чата через сервер;
- потоковые частичные ответы;
- изображения, аудио и остальные OpenRouter endpoints.

Эти пункты входят в следующие этапы тестовой ветки `test/server-mode-v1.18`.
