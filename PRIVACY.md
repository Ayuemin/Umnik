# Приватность Umnik

Umnik — локально ориентированное Android-приложение для работы с ИИ-моделями, проектами, чатами и базами знаний. У приложения нет обязательного облачного аккаунта Umnik и нет встроенного API-ключа автора.

## API-ключи и токены

Пользователь вводит собственный API-ключ OpenRouter. Он хранится в приватном хранилище приложения, шифруется AES/GCM, а ключ шифрования хранится через Android Keystore. API-ключ не должен попадать в диагностические логи и не отправляется автору Umnik.

Если пользователь включает необязательный личный сервер, токен этого сервера также хранится на устройстве в зашифрованном виде через Android Keystore. Сам сервер разворачивается на VPS, который выбирает и контролирует пользователь.

## Что хранится на устройстве

В локальном хранилище могут находиться:

- история чатов;
- проекты, этапы и настройки Оркестратора;
- навыки и рабочие файлы;
- исходные документы баз знаний, извлечённый текст, фрагменты, embedding-векторы и локальный индекс;
- пользовательский профиль, если он заполнен;
- настройки моделей и интерфейса;
- служебные записи Batch- и Video-задач;
- временные записи восстановления запросов;
- диагностический журнал, если пользователь явно включил его.

Recovery-запись прямого текстового запроса может содержать идентификаторы запроса, чата и сообщения, Generation ID, технический статус, точный JSON-payload и SHA-256-отпечаток API-ключа. Сам API-ключ в этой записи не хранится.

Для серверного режима временно сохраняются идентификатор серверной задачи, адрес личного сервера, модель и JSON-payload, необходимые для безопасного получения уже запущенной задачи после перезапуска приложения.

## Прямой режим

В прямом режиме необходимые данные отправляются с телефона в OpenRouter. В зависимости от функции это могут быть:

- текст текущего сообщения и часть истории;
- системные и проектные инструкции;
- подключённые навыки;
- рабочие файлы и вложения;
- параметры reasoning и web search;
- текст для Speech/TTS;
- аудио для Transcription/STT;
- данные специальных OpenRouter-функций, которые явно запускает пользователь.

OpenRouter может передать запрос выбранному провайдеру модели. Обработка этих данных регулируется условиями OpenRouter и соответствующего провайдера.

## Личный сервер

Личный сервер необязателен. Если пользователь выбирает **Через сервер**, обычный текстовый запрос отправляется сначала на его VPS, а VPS выполняет запрос к OpenRouter.

На VPS могут временно или постоянно находиться:

- payload текстового запроса;
- модель и служебный `client_request_id`;
- статус задачи;
- готовый ответ OpenRouter;
- текст ошибки;
- время создания и обновления задачи.

Эти данные хранятся в SQLite на VPS пользователя. OpenRouter API-ключ в серверном режиме находится в конфигурации этого VPS. Пользователь отвечает за доступ к серверу, резервные копии и выбранного VPS-провайдера.

Изображения, аудио, video, batch и другие специальные endpoints в текущем серверном протоколе продолжают выполняться напрямую с телефона.

## Фоновая работа и восстановление

На Android 14+ Umnik использует User-Initiated Data Transfer jobs для длинных запросов, которые пользователь запустил сам. Android или прошивка производителя всё равно могут остановить такую работу.

При прерывании прямого запроса Umnik не делает скрытый повтор оплачиваемого POST. Если OpenRouter уже предоставляет безопасный read-only способ получить состояние или сохранённый результат существующей генерации, приложение использует его. Иначе запрос помечается как прерванный и пользователь решает, повторять ли его вручную.

В серверном режиме повторное обращение телефона с тем же `client_request_id` идемпотентно: сервер возвращает уже созданную задачу вместо создания второй генерации. Ручная кнопка **Стоп** удаляет локальную запись восстановления, поэтому завершившаяся позже серверная задача не должна автоматически появиться в чате.

## Базы знаний и embeddings

Документы и индекс базы знаний хранятся локально, но создание embeddings выполняется через OpenRouter.

При индексации Umnik локально извлекает текст и разбивает его на фрагменты, затем отправляет текст фрагментов в OpenRouter Embeddings. При поиске текст запроса также отправляется в OpenRouter Embeddings. Сравнение векторов и выбор релевантных фрагментов выполняются на устройстве.

База знаний поэтому не является полностью офлайн. Не следует добавлять материалы, которые пользователь не готов передавать OpenRouter для создания embeddings.

## Оркестратор

Оркестратор может запускать другие чаты проекта, передавать между ними результаты и доступные файлы и временно менять параметры отдельного запуска. В прямом режиме целевые запросы идут в OpenRouter с телефона. При поддерживаемом серверном текстовом запросе они могут идти через личный VPS в соответствии с выбранным режимом подключения.

## Микрофон, веб-поиск и озвучивание

Разрешение на микрофон используется только после явного запуска записи. Umnik не ведёт постоянную или скрытую фоновую запись.

При включённом веб-поиске запрос может дополнительно обрабатываться механизмами поиска OpenRouter и связанными поставщиками.

Локальная Android Text-to-Speech зависит от установленного TTS-движка. При OpenRouter Speech текст отправляется в OpenRouter для генерации речи. Временная озвучка ответа используется для текущего воспроизведения; отдельный режим озвучивания может создать сохраняемый файл только после явного действия пользователя.

## Диагностика

Диагностика включается вручную. Журнал может содержать технические события: выбранный режим, тип модели, сетевой этап, HTTP-статус, длительность, тип вложения, фоновые задания и stack trace.

Диагностика не должна записывать API-ключи, токены сервера, содержимое личных сообщений, содержимое пользовательских файлов или текст фрагментов базы знаний.

## Телеметрия

Umnik не содержит отдельного SDK аналитики, рекламного SDK или обязательной серверной телеметрии автора приложения.

При изменении маршрута данных этот документ должен быть обновлён до публикации соответствующего релиза.
