# Приватность Umnik

Umnik - локально ориентированная Android-среда для работы с ИИ-моделями, проектами, специализированными чатами и базами знаний. В приложении нет собственного серверного аккаунта Umnik и нет встроенного API-ключа автора.

## API-ключи

Пользователь вводит собственный API-ключ OpenRouter.

Ключи:

- хранятся в приватном хранилище приложения;
- шифруются AES/GCM;
- ключ шифрования хранится через Android Keystore;
- не записываются в репозиторий;
- не отправляются автору Umnik;
- не должны попадать в диагностические логи.

## Что хранится локально

В локальном хранилище приложения могут находиться:

- история чатов;
- настройки проектов и этапов работы;
- настройки ◆ Оркестратора и профили проектных чатов;
- импортированные навыки;
- файлы проектов;
- постоянные файлы конкретных чатов;
- созданные моделью файлы;
- исходные документы базы знаний;
- извлечённый из них текст;
- фрагменты базы знаний;
- embedding-векторы и локальный индекс;
- метаданные источников базы знаний, включая номера страниц PDF, когда они доступны;
- короткий пользовательский профиль, если он заполнен;
- настройки интерфейса и выбранных моделей;
- служебные записи фоновых Batch- и Video-задач;
- временные записи восстановления обычных текстовых запросов: идентификаторы запроса/чата/сообщения, Generation ID, статус response cache, точный JSON-payload запроса и SHA-256-отпечаток использованного API-ключа; сам API-ключ в этих записях не хранится;
- диагностический журнал, если пользователь явно включил его запись.

## Что отправляется наружу

Когда пользователь запускает запрос, Umnik отправляет необходимые данные через OpenRouter. В зависимости от функции это могут быть:

- текст текущего сообщения;
- часть истории диалога;
- системные инструкции;
- мастер-инструкция и этапы проекта;
- выбранные навыки;
- файлы проекта;
- постоянные файлы текущего чата;
- разовые изображения, аудио, видео или документы;
- текстовые материалы отдельных Batch-задач;
- параметры reasoning и web search;
- текст, переданный для Speech/TTS;
- аудио, переданное для Transcription/STT.

OpenRouter может передать запрос выбранному провайдеру модели. Обработка этих данных регулируется условиями OpenRouter и соответствующего провайдера модели.

## Базы знаний и embeddings

Базы знаний Umnik используют RAG и локальное хранение индекса, но создание embeddings в текущей версии выполняется через OpenRouter.

### При индексации документа

Umnik локально извлекает текст и разбивает его на фрагменты. Затем текст фрагментов отправляется в OpenRouter Embeddings для вычисления embedding-векторов.

После получения результата Umnik хранит локально:

- исходный документ;
- извлечённый текст;
- фрагменты;
- embedding-векторы;
- индекс и метаданные.

### При поиске по базе знаний

Текст поискового запроса отправляется в OpenRouter Embeddings для получения embedding запроса.

Сравнение embedding запроса с локальным индексом и выбор наиболее релевантных фрагментов выполняются на устройстве. После этого основной ИИ-модели передаются только выбранные фрагменты, а не весь большой источник.

Таким образом, база знаний является локальной по хранению индекса и документов, но **не полностью офлайн**: текст при первичной индексации и текст поисковых запросов обрабатываются OpenRouter Embeddings.

Пользователю не следует добавлять в базу знаний материалы, которые он не готов передавать OpenRouter для создания embeddings.

## Фоновое восстановление запросов

Если сетевое соединение или процесс Android прерываются после отправки обычного текстового запроса, Umnik может временно сохранить локальную recovery-запись, чтобы попытаться получить уже созданный ответ без слепой повторной генерации.

Такая запись может содержать точный JSON-payload исходного запроса, поэтому в ней присутствует тот же текстовый контекст, который пользователь уже разрешил отправить OpenRouter. Запись хранится только во внутреннем каталоге приложения и удаляется после успешного восстановления, явной отмены или окончательной ошибки.

API-ключ OpenRouter в recovery-запись не помещается. Вместо него сохраняется только SHA-256-отпечаток для проверки, что при восстановлении используется тот же ключ из зашифрованного SecretStore.

Автоматический replay разрешается только когда OpenRouter подтвердил участие исходного ответа в response cache. Если это не подтверждено, Umnik не делает скрытый повтор, чтобы снизить риск двойного списания.

## ◆ Оркестратор и передача между чатами

◆ Оркестратор может выполнять другие чаты проекта, передавать между ними результаты и доступные файлы и временно менять параметры отдельного запуска.

Такие действия не создают отдельный сервер Umnik. Когда целевой чат обращается к модели, его необходимый рабочий контекст отправляется через OpenRouter так же, как при обычном ручном запросе.

Результаты выполнения сохраняются локально в историях целевых чатов и в журнале Оркестратора.

## Микрофон и голосовые сообщения

Разрешение на микрофон используется только после явного запуска записи пользователем. Umnik не ведёт постоянную или скрытую фоновую запись.

Запись создаётся локально на устройстве и отправляется наружу только после действия пользователя, требующего обработки этой записи. При отмене запись не отправляется модели.

## Web search

Если пользователь включает **Поиск в сети**, запрос может дополнительно обрабатываться механизмом веб-поиска OpenRouter и связанными с ним поставщиками поиска.

## Озвучивание

В Umnik есть два варианта озвучивания ответа:

- локальная Android Text-to-Speech, поведение и политика которой зависят от установленного на устройстве TTS-движка;
- OpenRouter Speech по кнопке `OR`: текст ответа отправляется в OpenRouter для генерации речи.

Временная `OR`-озвучка ответа не добавляет MP3 в историю чата и не сохраняет его как постоянный файл Umnik. Полученные аудиофрагменты используются для текущего воспроизведения во временном кэше и удаляются после остановки или завершения.

Отдельный режим **Озвучить** может создавать сохраняемый аудиофайл, когда пользователь явно запускает эту функцию.

## Диагностика и логи

Диагностика включается пользователем вручную. Журнал предназначен для поиска ошибок и может содержать технические события: выбранный режим, тип модели, сетевой этап, HTTP-статус, длительность, тип вложения, возврат результата и stack trace ошибки.

Диагностика не должна записывать:

- API-ключи;
- содержимое личных сообщений;
- содержимое пользовательских файлов;
- текст фрагментов базы знаний.

Перед передачей журнала другому человеку пользователь может просмотреть сохранённый файл самостоятельно.

## Телеметрия

На текущем этапе Umnik не содержит отдельного SDK аналитики, рекламного SDK или собственной серверной телеметрии автора приложения.

При добавлении функций, меняющих обработку данных, этот документ должен быть обновлён до публикации соответствующего релиза.
